# 阶段 D　基于开源项目二次开发

场景：接到一句话需求，要在一个完全陌生的开源框架上做二次开发。典型例子：在一个 Agent 框架上搭一套 7×24 运行的混沌测试系统。代码不是你的，用法是你的。

整条流水线：

```text
建立学习框架 → 第一次翻译（需求 → 设计文档）→ 路径反问 → 第二次翻译（设计 → 方案文档）
→ 跑通 HelloWorld，回看方案 → 提示词驱动写代码（先通用代码层，后业务层）→ 整体点评 → 跑通验证 → 7×24 运行
```

贯穿全阶段的主张：
1. 拆解框架是人的能力，AI 只负责把框架填得又快又准。提问必须带着具体任务。
2. 一句话需求藏着的事，比它说出来的多。先拆成文档，再动手。改文档比改代码便宜得多。
3. 设计文档和方案文档是之后开发的单一事实源。代码偏离了文档，要么改代码，要么改文档，然后重新对齐。
4. **方案落地前，必须反问「路径选对了吗」。** 刚摸过的框架，可能已经做好了 80% 的工程。
5. 不要通读文档。先跑通最小闭环，遇到卡点再回头读文档的对应章节。
6. 提示词公式：**接口签名 + 硬约束 + 已有依赖。** 你已经想到的写进去，剩下的空间留给 AI。
7. 开发顺序：被依赖的先写，工具先写，说明文件最后写；通用代码层先于业务层。
8. 人的价值在三处：定方向、拍板；检查跨文件的语义是否一致；把关长期运行的风险（时间函数、容量、超时）。

在开源项目的仓库目录下执行。产出：
- `make-skill-legacy-takeover-output/1-framework-map.md`（框架地图，D1）；
- `make-skill-legacy-takeover-output/2-plan.md`（模板 `templates/plan-oss.md`：第一部分设计，D2–D3；第二部分技术方案，D4）；
- `make-skill-legacy-takeover-output/diagrams/boundary.svg`、`run-chain.svg`；
- 代码，按方案里的目录放（多数框架的扩展放在用户目录，不在仓库里）；
- 总说明 `make-skill-legacy-takeover-output/README.md`（模板 `templates/output-README.md`，开工时就建，进度表换成 D1–D8）。

**两种运行方式**（见 SKILL.md 第 2 节）：只读（默认）做 D1–D4，出框架地图和方案，然后直接 D8 收尾；用户说「跑起来」才做 D5–D7（装框架、写扩展代码、跑通）。

**四个决策点**（必须由人拍板的点）：
1. 第一次翻译里的关键选择；
2. 路径选择；
3. 方案的决策记录；
4. 业务层的场景库范围。

其中**路径选择问用户一次**，另外三个按「AI 推荐，待确认」处理，写进总说明的「待你确认的 AI 推荐」。

**耗时参考**（用于「超过预估 1.5 倍就停」的规则）：
- 设计文档：20–30 分钟
- 跑通框架：20–30 分钟
- 代码层：1.5–2 小时
- 业务层：约 1 小时
- 全流程：4–5 小时

## D1　建立学习框架

先定自己的四维拆解框架：
- **它是什么**：定位和边界；
- **它能做什么**：原生能力清单；
- **它怎么扩展**：扩展点长什么样；
- **内部机制**：运行时、状态、接入面。

第 1 维和第 4 维合并成一个提示词，总共三个提示词。每个提示词都带着具体任务，在仓库目录里读 README、架构文档、顶层目录。

执行规格 1（定位 + 机制）：

```plain
你现在在 <框架名> 这个开源项目的目录下。我刚接到一个任务:
要基于 <框架名> 做 <一句话需求，展开列出要做的功能>。

请你读 README、docs/ 下的架构文档和 src 顶层目录结构，告诉我:

1. <框架名> 的核心定位是什么。一句话说清楚。
2. <框架名> 的核心抽象有哪些。每个抽象用一句话解释它的作用。
3. <框架名> 不解决什么问题。它的设计边界在哪。
4. <框架名> 是怎么跑起来的。进程模型、配置加载、状态管理大致是什么样。
5. 结合我接到的任务，<框架名> 的定位是不是和我的需求方向一致。有没有明显的不匹配。

不要复述官方话术。用你判断后的结论来回答。
```

「不解决什么」比「能做什么」更值钱：框架不解决的那几块，正好就是你要自己写的核心。

执行规格 2（能力对照）：

```plain
继续。我的任务需要这些能力，请对照 <框架名> 现有功能，
告诉我每一项能不能直接用、用哪个特性、还需要我自己实现什么:

1. <能力 1，如定时触发>
2. <能力 2，如调用工具函数>
...

输出格式:每一项分别说，<框架名> 直接支持哪些、半支持哪些(需要简单配置)、
完全不支持哪些(需要我自己写)。
最后给我一个总结，我自己要写的工程量大概有多大。
```

执行规格 3（扩展点）。用疑问句，给 AI 留出纠正你预设的空间：

```plain
继续。如果我决定用 <框架名> 做这个系统，我自己要写的核心是 <你预设的扩展点> 吗？
如果是，请深入读相关文档和 examples/ 下的几个示例，告诉我:

1. 它是什么形状。目录结构、关键文件、一个最小实现包含哪几样。
2. 里面的工具/函数怎么定义。函数签名、参数类型、返回值约定。
3. 它们之间怎么共享状态。
4. 说明文件是给谁看的、写什么内容、有没有写法约定。
5. 给我一个最小可行的骨架，假设它只做一件事:
   返回当前时间。让我能判断扩展一个的工程量大概多大。

不要泛泛而谈，我要的是能直接用来评估开发量的具体认知。
```

**回到官方文档核一遍**：AI 的总结会丢东西，丢的恰恰是体系化认知需要的那部分。三个提示词跑完以后，拿框架地图里的关键结论（核心抽象、扩展点的形状、它不解决什么），回到官方文档原文逐条核实，并标注来源（文件、章节）。目标是「大概看懂，知道有什么」，不是通读。

产出 `make-skill-legacy-takeover-output/1-framework-map.md`：
- 定位、核心抽象（附文档来源）；
- 「不解决什么 → 我要补的位置」对照；
- 能力对照表（直接支持 / 半支持 / 不支持）；
- 「白嫖区 / 开发区」边界图（SVG：`make-skill-legacy-takeover-output/diagrams/boundary.svg`）；
- 工程量估计。

自检：
- [ ] 能回答三个问题：框架适不适合这个任务？会直接用到哪些核心抽象？运行时模型对部署有什么影响？
- [ ] 被纠正的预设记下来了（实践中的例子：预设「核心是 Skill」，实际是 Tool，Skill 只是 Tool 的使用说明书）
- [ ] 关键结论都对照官方文档核实过，并标了来源

## D2　第一次翻译：一句话需求 → 设计文档

先把一句话需求没说出来的事列清楚：测什么、频率、产出给谁、覆盖哪些组合。每一个选择都会影响方案。

执行规格（展开）：

```plain
帮我把这个一句话需求展开成完整的技术设计文档：<一句话需求>。

这一步先别谈具体技术框架，把"为什么要做、做什么、不做什么、用什么思路、
覆盖什么场景、产出什么"讲清楚。

有几个我自己一时拍不准的关键选择，你列出来给我看，每个给两三个选项和
影响，我来拍。

不要复述，要展开。
```

这段提示词有三个设计要点：
- 「先别谈技术框架」，把需求和技术栈解耦；
- 「列出我拍不准的选择」，让 AI 把要人拍板的点显式列出来；
- 「不要复述，要展开」。

**反问补漏**：拿你对「一份完整的设计文档应该长什么样」的预期去比对，差什么就补什么。常见的空洞有：场景没有分优先级；产出给谁看（对内还是对外，会影响存储和脱敏）没说清；覆盖矩阵不够系统。

```plain
你这版有几处空洞：

1. <空洞 1，补什么>
2. <空洞 2，给两三个选项>
3. <空洞 3，展开>

别又冒新选择，把这版补完整。
```

反问的写法是「这里漏了，补上」，不是继续追问。发散阶段和收敛阶段要在提示词里分清楚，否则方案永远定不下来。

**整合**：显式列出必须包含的节，否则 AI 凭近期的对话回忆，会漏东西。

```plain
基于前面两轮讨论，把所有产出整合成一份完整的技术设计文档，
能拿出去给社区评审的那种。

至少包括：
1. 背景和目标(为什么做)
2. 系统设计思路
3. 能力清单(每项的签名级职责)
4. 场景库分级(P0/P1/P2，对应触发频率)
5. 覆盖矩阵(完整表)
6. 归因表(发现的问题 → 具体在哪里改)
7. 产出公开度决策

写进 make-skill-legacy-takeover-output/2-plan.md 第一部分「设计」。
```

结构按 `templates/plan-oss.md` 第一部分。每个关键选择都写出推荐选项和理由，标「AI 推荐，待确认」。

自检：
- [ ] 六块都有内容：为什么、做什么、不做什么、思路、场景、产出
- [ ] 待拍板的选择至少 3 个，每个都有选项和影响，不是空泛的「由你决定」
- [ ] 归因表把「发现问题」转成了「在哪里改」，后面的报告模板会反复用到它

## D3　路径反问（硬约束，问用户一次）

```plain
等一下。基于这份设计文档，但先别按"自研"的路径走。

我刚刚摸过 <框架名>。它自带：<从框架地图的白嫖区列出的能力>。
这套系统需要的"<需求的组成部分>"里，<哪些部分> <框架名> 都有了。

帮我对比两个路径：
1. 按设计文档原方案，自研
2. 把这套系统建在 <框架名> 之上

每个路径分别要做什么、各自的工程量、各自的演进空间。
```

对比结果写进 `2-plan.md` 第一部分的附录，然后问用户：「建议走 <路径>，理由 <…>。确认吗？」

用户事先说过「不用问」的，按推荐路径走，在总说明「需要你做的事」第一条注明。

## D4　第二次翻译：设计 → 方案文档

执行规格：

```plain
方向定了，基于 <框架名> 重写技术方案。需要包括：

1. 整体架构和部署方式
2. 扩展怎么设计？一个套件还是多个独立单元？目录结构什么样？
3. 工具函数怎么映射到框架的扩展点，每个怎么实现？
4. 场景库/业务数据怎么放？怎么让框架读？
5. 触发机制
6. 产出/报告系统
7. 关键决策记录(每条带选定方案和理由)
8. 实施步骤(按依赖顺序)

记得结构化的东西用代码生成，JSON 别交给 LLM 写。
```

**反问收紧**：

```plain
你这版有几处可以再收紧：

1. <边界原则，如套件粒度：以后再加新能力时边界怎么划>
2. <选型判断标准：什么场景用哪个>
3. <凭据怎么管、放哪、怎么读>

补这三条，别又冒新决策。把这版收紧。
```

**整合**到 `make-skill-legacy-takeover-output/2-plan.md` 第二部分「技术方案」，结构按 `templates/plan-oss.md` 第二部分（这是二次开发专用的模板，不是改造阶段那份）。运行链路图 `diagrams/run-chain.svg` 在这一步就画出来（画法见 D6 开头），引用在第二部分第 1 节。整合提示词里显式列出必须包含的内容，否则会漏：

```plain
把以上内容整合成完整方案文档，写进 make-skill-legacy-takeover-output/2-plan.md 第二部分。必须包含：
路径对照表、目录树、各工具实现要点、场景库分级、触发机制、凭据方案、关键决策记录、按依赖排序的实施步骤。
```

方案写完放一晚，第二天再看一遍。一口气跑完的，就在总说明里提醒用户第二天复看。

自检：
- [ ] 每一个技术决策，都能追溯到设计部分的某一条需求
- [ ] 实施步骤的每一步，产出都能独立验证

## D5　先跑通 HelloWorld，再回看方案（D5–D7 只在运行方式下）

只读方式到 D4 为止，直接做 D8。D5–D7 要做的事（安装、要写的单元清单、凭据、调度）写进总说明「需要你做的事」，用户说「跑起来」后接着做。

不通读文档，先装到能跑就行，环境花一两个小时，不追求完美。遇到坑再去读文档的对应章节。

1. 安装框架。需要人操作的步骤写进总说明。
2. 用三个指令建立手感：自我介绍、跑一个 shell、简单查询。顺带试一下帮助、工具列表、模型切换这类命令。观察：它什么时候调用工具、会不会先确认、返回什么格式、速度怎么样。
3. 写一个最简单的工具（例如返回当前时间，约 20 行：函数、参数 schema、注册），放在框架指定的用户目录，**不要放进仓库源码目录**。
4. 写一个最简单的说明文件（frontmatter 写 name、description、version；正文写「什么时候用」和「步骤」）。
5. 用对话触发，验证这两个都能被调用到，并且在列表命令里能看到。
6. 记录踩坑：
   - 没注册：检查文件位置、名字、要不要重启；
   - 没加载：检查目录结构、name 字段、description 写得清不清楚；
   - 参数错：工具的 description 是写给 LLM 看的，要写清楚。
7. 回看方案，画一张**分三类的文件分布表**：

   | 类 | 内容 | 放在哪 | 说明 |
   | --- | --- | --- | --- |
   | 扩展本体 | 工具、说明文件、场景库、模板、套件配置 | 框架的用户扩展目录 | 和框架松耦合，能整体搬走 |
   | 框架全局配置 | 调度配置；**审批模式 + 命令白名单** | 框架的全局配置文件 | **无人值守的安全护栏**。7×24 运行最容易翻车的就是凭据和白名单：需要执行的命令（起停进程、git push 等）要显式加进白名单，审批模式设成无人值守可以用的那种 |
   | 外部凭据与仓库 | 密钥、报告仓库 | 用户目录，比如 `~/.ssh/` | 只授予单个仓库的写权限，通过环境变量指定，不进框架的 .env，也不进版本库 |

   首期的触发通道只做 CLI 和定时调度，IM 之类的其他通道放到第二期。

8. 按依赖顺序确定第一个要写的单元。判定方法：
   - 被其他所有单元假设已存在的资源（集群、连接、环境），最先写；
   - 能独立验证的观测类，第二；
   - 依赖前面产出（比如 endpoint）的，第三；
   - 汇总类（报告），最后；
   - 说明文件，排在所有工具之后。

## D6　让代码长出来

### 动手前先把运行链路想清楚

运行链路图（SVG：`make-skill-legacy-takeover-output/diagrams/run-chain.svg`）在 D4 已经画好，引用在 `2-plan.md` 第二部分；写代码前再核对一遍：

```text
触发源（定时 / 手动）→ 指挥层（Agent + 说明文件）→ 执行层（各工具）→ 数据层（产出、仓库）
```

然后从链路反推出「要写的单元清单」。

本阶段只做**通用代码层**（工具 + 说明文件骨架），业务层（场景、模板、配置、凭据、调度）留给 D7。这样切的原因：代码层是通用的，可以搬到别处复用；业务层绑定具体项目。

### 每个工具的执行规格模板

```plain
帮我写 <路径>/<tool>.py。

这是 <套件名> 的第 N 个 Tool，负责 <职责>。
按 make-skill-legacy-takeover-output/2-plan.md 的决策：<相关决策>。

action 支持 <a> / <b> / <c>。

<a>: <具体行为、参数、成功返回的 JSON 结构、失败时的处理>
<b>: ...

<配置/路径> 通过 <环境变量或配置文件> 取，没设置就 fail-fast 返回 error，别用默认值兜底
(默认值会让人误以为路径配对了)。

handler 函数签名 <签名>，失败返回 {"error": "..."} 别抛异常(Agent 循环见到异常会中断)。
```

### 规则

- **范围控制**：第一版只实现最核心的最小集（比如故障类型先只做 2 种），其余返回 `not_implemented`。不要让 AI 一次写全。
- **脚本协议**：被调度的外部脚本和调度它的工具之间，要约定好协议。一个好用的约定是：stdout 最后一行输出约定字段的 JSON，exit code 表示通过还是失败。JSON 解析失败的，单独记成 `script_format_error`，不要和测试失败混在一起算。
- **并发放在工具内部**（比如用线程池），不依赖框架的子 Agent、delegate 机制。
- **结构化产出用代码生成**：JSON 用 `json.dumps`，Markdown 用模板渲染。绝对不要让 LLM 写 JSON。
- **通过判定写成可以计算的规则**，阈值来自设计部分，放进配置文件。比如：单场景通过 = exit_code=0 且 lost=0 且 p99<500ms；整轮通过 = 核心场景全部通过，且非核心场景通过率 ≥ 75%。
- 报告类工具顺手清理过期的本地临时文件（比如清理 30 天前的）。

### 说明文件（Skill）的执行规格要点

- 把所有工具的接口 schema **完整喂给 AI**，并写上「直接照着调，别编不存在的字段」。不喂的话，AI 会编出根本不存在的工具调用，加载后一跑就报错。
- frontmatter 里把依赖的工具列全（比如 `requires_tools`）。
- 「什么时候用」要分别写清楚：定时触发怎么识别、手动触发怎么识别。
- 骨架：前置检查（确认没有残留的进程）→ 单场景执行步骤 → 通过 / 失败判断 → 产出归档 → Pitfalls。
- **核心业务规则**（这是整个 Skill 最重要的一条）：故障期间只记录、不判断；故障窗口结束、自动恢复以后的**自愈验证，是 pass/fail 的唯一依据**。泛化到其他业务：过程中的数据只记录，以最终状态验证为准。
- 熔断：连续失败时怎么暂停调度，必须写清楚，不能留白。
- 具体场景先留白，到 D7 用单独的提示词填。

### 单点验证

每写完一个工具，就在对话里让框架调用它一次。框架真去调了、返回了结果，这个工具就是活的。调不通的，九成是 description 没写清楚，或者参数 schema 不合法，回到提示词里改两句重跑。

自检（每个工具都过一遍）：
- [ ] 硬约束都做到了：fail-fast；临时资源有清理；**启动类操作失败时，回滚已经创建的资源**（比如起了一半就把已起的全部 kill 掉）；失败返回 error，不抛异常；配置不硬编码
- [ ] 结构化输出用代码生成；解析失败单独记状态
- [ ] 第一版的范围没有超出最小集

## D6.5　整体点评

全部代码写完以后，退一步通读一遍，用最小的改动把漏洞堵上。**把关不是重写。**

检查项：
1. **等待不要写死 `sleep N`**：要轮询（比如每秒探测一次，最多 30 秒），超时参数做成可配置的。
2. **区分「探针失败」和「工具出错」**：比如故障注入以后，目标进程本来就该不可达，这是预期内的。返回里要加 `reachable: false` 这类字段，别让 Agent 把它误判成异常而中止。
3. **跨文件的语义要一致**：比如「恢复接口返回成功」不等于「目标已经恢复健康」，工具的 description 要写明这一点。说明文件里「恢复后等待 N 秒」这样的写法，必须改成「先验活（健康检查返回 200），再开始计时」。
4. **静默行为至少打一行日志**：版本切换被跳过、重名的场景被覆盖这类事，至少打一行 debug 或 warning 日志。
5. **跑半年以后的风险**：时间函数和时区、超时、容量（比如每次都完整 clone 一遍仓库，会越来越慢，应该改成持久的本地 clone 加 pull），至少记一条 TODO。

点评发现了什么、怎么处理的，写进总说明「做了什么」的 D6.5 一项。

## D7　填业务层，跑通

1. **第一个场景文件**：场景描述是写给 Agent 看的可执行说明。每个场景一个独立文件，Agent 一次只加载本轮要跑的那几个。写完第一个，其余的套用同一个模板。
   - 场景清单（分级和数量）是四个决策点之一，写进总说明的「待你确认」。
   - 自检：故障类型和参数，和工具的接口对得上；通过标准里的字段名，和工具返回的 JSON 对得上。
2. **报告模板**：
   - 结构：顶部一段 summary，每个场景一个二级标题，结果用表格，底部一段归因（规则取自设计部分的归因表）；
   - 长度不超过约 80 行；
   - 纯模板语法，**不在模板里调 LLM**；
   - 几种归因都没命中的，标「待人工分析」，不要在边界 case 上偷懒。
3. **套件配置**：按方案的决策填值。P0 档刻意保持最小，跑得越快越好；大矩阵留给 P1、P2。
4. **凭据**：在总说明的「需要你做的事」里，给出一份可以直接复制的命令清单：
   - 生成专用密钥（比如 ed25519，自动化用，无口令）；
   - 创建报告仓库；
   - 在仓库设置里添加 Deploy Key，**勾选 Allow write access**（默认是只读的）；
   - 做一次初始化提交，确保第一次 push 能成功；
   - 用环境变量（比如 `GIT_SSH_COMMAND`）指定密钥。

   在密钥配好之前，报告工具只验证本地生成的 JSON 和 Markdown，标注「push 要等你配好密钥后再验证」。
5. **无人值守护栏**：生成审批模式和命令白名单的配置草稿（D5 第 7 步的第二类）。不要替用户改框架的全局配置，草稿写进总说明的「需要你做的事」。
6. **调度配置**：频率直接来自设计部分的分级，同一档的任务错开时间，避免资源冲突。**先只写草稿，不启用。**
7. **跑通验证**（必须在启用调度之前做）：
   1. 列表命令里能看到工具和说明文件都加载了；
   2. 用对话手动跑一轮 P0 场景，每一轮工具调用都记录下来；
   3. 产出（报告等）落到了预期的位置。

   **手动跑通了，定时调度才能放心装上自动跑。** 验证通过以后，在总说明里标「调度可以启用」，并附上启用的步骤。

## D8　收尾

按 SKILL.md 第 9 节补全总说明 `make-skill-legacy-takeover-output/README.md`。二次开发模式下，各节写这些：
- **做了什么**：D1–D8 各做了什么；点评发现及处理（运行方式）；每个工具的单点验证结果、跑通验证的结果（运行方式）；
- **需要你做的事**：安装、凭据、白名单和审批模式、启用调度；第二天复看方案的提醒；只读方式下加一条「说『跑起来』开始写扩展代码」；
- **待你确认的 AI 推荐**：四个决策点的结论，即第一次翻译的关键选择、路径选择、方案决策记录、场景库范围。除路径外，都是「AI 推荐，待确认」；
- **产出物一览**：`1-framework-map.md`、`2-plan.md`、两张图；
- **代码改动**：扩展代码放在哪里（多数不在仓库里，写出完整路径）。只读方式写「没有写代码」。

人重点把关的三件事：方向和拍板；跨文件的语义是否一致；长期运行的风险。
