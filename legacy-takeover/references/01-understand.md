# 阶段 A　摸项目

目标：从 `git clone` 到「AI 协作基础设施」就位。交付项目地图 `1-project-map.md`（应用架构、技术架构、模块说明、风险地带、模块依赖、外部依赖、接口清单、数据模型、核心时序，配五张 SVG 图）、要放到项目根目录的 CLAUDE.md、第一个项目 SKILL（docs-auto-sync），外加写在总说明里的疑点清单。

**这一阶段只读代码，不运行项目**，两种运行方式下做法一样。

## 背景：八步心法（指导本阶段的每个判断）

目标不是读懂全部代码，而是建立「足以推进改造」的锚点：核心链路、高风险模块、对外契约、历史坑。要避开两种失败：通读全部代码却没有锚点；交出一份看着漂亮、实际没核实的总结。

1. 读 README 和根目录文档，得到最粗的轮廓：做什么、跑在什么环境、核心概念有哪些。
2. 扫项目结构，得到模块地图：分几块、各干什么、哪些是核心、哪些是边缘。
3. 找核心入口：HTTP 找 controller / main，定时任务找调度注册的地方，消息找 consumer / listener。入口是坐标原点。
4. 画项目全景：应用架构图、技术架构图（含外部依赖）、模块依赖图，再给每个模块写说明。
5. 梳理接口和数据模型：得到输入输出和核心抽象。
6. 搭环境跑起来（阶段 B）。
7. 带需求深挖代码（阶段 C）。
8. 沉淀成 AI 能读的文档：CLAUDE.md、SKILL.md。

三条原则：
- 螺旋，不是线性：可以回头改，但八步都要走到。
- 每一步都落盘：没有沉淀，等于没做。
- 建立锚点，不追求读懂。

## A0　准备

```bash
mkdir -p make-skill-legacy-takeover-output/diagrams make-skill-legacy-takeover-output/apply/.claude/skills
```

- 从 `templates/project-map.md` 建立 `make-skill-legacy-takeover-output/1-project-map.md`。A1–A6 的结论都写进它对应的小节，不另建文件。小节顺序是：1 应用架构、2 技术架构、3 模块说明、4 风险地带、5 模块依赖、6 外部依赖、7 接口清单、8 数据模型、9 核心接口时序、10 互校结果。下文按小节名引用。
- **所有的图都是 SVG 文件**，放在 `make-skill-legacy-takeover-output/diagrams/`。画法、配色、自检流程见 `references/svg-diagrams.md`，底稿是 `templates/diagram-base.svg`。默认直接手写 SVG。本机有 claude-mermaid 或 mermaid-cli（`mmdc`）时，也可以先写 Mermaid 再渲染成 SVG，但交付的只能是 SVG 文件，文档里只用图片链接引用。不要为了画图去全局安装软件。

画图规范（所有图通用，细节见 `svg-diagrams.md`）：
- 分层，用分组框把同一层的节点框起来；
- 同类同色：核心用石墨蓝，周边用暖灰，外部依赖用橙色（三类外部依赖再用深浅区分）；
- 每个节点只写名字加一句话职责；
- 全项目统一一个方向，从上到下或者从左到右；
- 画完截图看一眼，文字不能溢出、不能重叠，连线不能穿过节点。

**一定要读真实文件，不能按名字脑补。**

## A1b　应用架构图

技术架构图回答「用什么技术搭的」，应用架构图回答「这个系统做什么、由哪些业务能力组成、谁在用、业务怎么流转」。新人和业务方最先要看的是这一张。

执行规格：

```plain
读一下这个项目的 README、前端路由和菜单配置、后端的包结构和 Controller 分组、数据表前缀，
给我画一张应用架构图。
按业务域分组，每个域列出它包含的应用模块，每个模块写一句话业务能力(写业务意图，不写类名)。
顶部画使用者：终端用户、管理员、外部系统、定时任务。
底部画各业务域共用的平台能力：鉴权、文件、消息、通知这类。
业务域之间画主要的业务流向(比如 下单 → 支付 → 通知)。
不画技术栈、中间件和部署，那是技术架构图的事。
保存到 make-skill-legacy-takeover-output/diagrams/app-architecture.svg。
```

产出：`make-skill-legacy-takeover-output/diagrams/app-architecture.svg`；业务域、模块和使用者的说明写进 `1-project-map.md`「应用架构」一节。

自检：
- [ ] 每个业务域、每个模块都能在代码里找到对应（包、Controller 分组、前端路由、菜单），来源写进小节里的表格
- [ ] 写的是业务能力（「订单创建与取消」），不是技术名词（「OrderServiceImpl」）
- [ ] 使用者齐全：有管理后台的画了管理员，有开放接口的画了外部系统，有定时任务的画了调度
- [ ] 菜单和路由里有、代码里找不到实现的功能，或者代码里有、菜单里没有入口的模块，记进总说明「疑点」，图上标黄

- [ ] 依赖方向是从构建文件里读出来的，没有画反（底层 core 不能反过来依赖上层）

## A4　REST 接口清单

执行规格：

```plain
扫一下这个项目里所有的 Controller，给我整理一份 REST 接口清单。
每个接口列出方法（GET/POST 等）、路径、一句话说明、主要入参、返回结构。
按模块分组。写进 make-skill-legacy-takeover-output/1-project-map.md「接口清单」一节。
```

追加要求：每个子模块都可能有入口，逐个扫；对外接口和内部接口（RPC、管理端）分开标注。结构按 `templates/project-map.md`「接口清单」一节：
- 小节开头写来源（扫了多少个入口文件）和统一返回结构；
- 然后是目录；
- 按模块分章，每章写 Base path，先放总表，再逐个接口写入参和返回；
- 流式（SSE）、文件流这类特殊返回要写明。

自检：
- [ ] 小节开头写的入口文件数量，和 `grep` 统计出来的数量一致。少了就补扫
- [ ] 每个接口的「一句话说明」写的是意图，不是方法名
- [ ] 返回结构写清楚了：有没有包装、是列表还是单个对象
- [ ] 字段细节没有在这里展开，留给数据模型

## A5c　模块说明

一句话职责只够认路。改造前真正要查的是：这个模块的入口在哪、核心类是什么、读写哪些表、依赖谁、改了会牵动谁。这一步把前面几张图和接口、数据模型串起来，落到每个模块上。

执行规格：

```plain
基于构建文件、包结构、应用架构图、模块依赖图、接口清单和数据模型，给每个模块写一份说明：
- 职责：一句话，写业务意图，不写类名
- 入口：对外接口(写路径前缀和数量)、定时任务、消息消费者
- 核心类：3-5 个，写文件路径
- 主要读写的表
- 依赖谁、被谁依赖
- 改动风险：高/中/低，写依据(被依赖多、有对外接口、有跑批、有疑点)
前端按页面或路由模块写：页面、调用的接口、共用组件。
疑似废弃的模块(没人依赖、没有入口、最近一年没人改)单独列出来，不要删，也不要当成核心。
写进 make-skill-legacy-takeover-output/1-project-map.md「模块说明」一节。
```

结构按 `templates/project-map.md`「模块说明」一节：先放总表，每个模块一行；核心模块（改动风险为高的）再各写一小段要点。

自检：
- [ ] 构建文件里的每个模块都在总表里，数量对得上
- [ ] 入口数量和接口清单对得上，表和数据模型对得上
- [ ] 改动风险有依据，没有全标「中」
- [ ] 疑似废弃的判断有证据（依赖关系、`git log` 最后修改时间），同时记进总说明「疑点」

## A7　疑点清单和禁区线索

这一步对应九步链路里的「找人聊」。人不在场时，你能做的是把要问的问题准备好。

1. 扫这几类线索：
   - 注释里的 `不要删`、`勿动`、`临时`、`兼容`、`hack`、`TODO`、`FIXME`、`deprecated`；
   - 没人引用却没删的类、方法、表、字段；
   - `git log` 里反复回滚、反复修补同一处的记录（`git log --oneline -- <文件>`）；
   - 意义不明的配置开关和默认值；
   - 曾经公开过的接口路径（README、SDK、OpenAPI 文档里出现过的）。
2. 每条写进总说明 `make-skill-legacy-takeover-output/README.md` 第六节「疑点」：编号 | 问题 | 证据（文件:行号 或 提交号）| 为什么重要 | 可能归属（禁区 / 历史包袱 / 其他）| 该问谁 | 状态（待问）。
3. 宁少勿多：只列改了以后可能出事的，最多 20 条。

## A7b　风险地带

这一步对应「识别风险地带」：理解层的产出，除了架构全景，还要有一份「哪里动不得、哪里一动就出事」的清单。前面的发现散在模块说明的改动风险、疑点清单里，这里汇总成一处，改造前先看它。

执行规格：

```plain
基于 make-skill-legacy-takeover-output/1-project-map.md 的模块说明、接口清单、外部依赖，
加上 git 历史，给我整理一份风险地带清单。看这几类：
- 改动热点：用 git log 统计近两年改动最多的文件，以及反复回滚、反复修补同一处的提交
- 没有接缝的老代码：改动风险高，又没有可覆写的方法、配置注入或接口可以隔离的类
- 有外部调用方的接口和字段：对外公开过的路径、被 SDK 或其他系统依赖的字段
- 跑批和定时任务：失败了不会马上被发现的地方
每条写：位置、类型、为什么危险、证据(文件:行号或提交号)、有没有接缝、改之前要做什么。
总数不超过 15 条，宁少勿多。写进 make-skill-legacy-takeover-output/1-project-map.md「风险地带」一节。
```

做法：
- 热点数字用命令跑出来，不估：`git log --since="2 years ago" --name-only --format= | sort | uniq -c | sort -rn | head -20`。这是只读命令，只读方式下也照做。仓库是浅克隆、或者历史被迁移截断时，写明「git 历史不完整」，热点一栏只列能确认的。
- 接缝的判断见 `00-methodology.md`：可覆写的方法、配置注入、接口，都算接缝；静态调用、new 出来的依赖、超长方法里的分支不算。
- 「测试兜底」一列先写「待阶段 B」，B9 摸完测试缺口后回来补。

自检：
- [ ] 每条都有证据，热点数字是命令跑出来的
- [ ] 风险写的是具体后果（「改了返回字段，某 SDK 客户的缓存键失效」），不是「可能出错」
- [ ] 涉及业务含义、说不清为什么的，不猜，同时记进总说明「疑点」
- [ ] 不超过 15 条

## A8　CLAUDE.md

执行规格：

```plain
读 make-skill-legacy-takeover-output/1-project-map.md 和五张图，给我生成一份 CLAUDE.md 初稿。
精简：项目定位、核心架构、关键模块、关键约定、怎么跑，
外加两节空着的：禁区、历史包袱。
架构图、接口清单、数据模型的详细内容不要复制进来，
用链接指向 make-skill-legacy-takeover-output/1-project-map.md 就好。保存到 make-skill-legacy-takeover-output/apply/CLAUDE.md(它以后会被放到项目根目录，所以链接按项目根目录写)。
```

结构按 `templates/CLAUDE.template.md`。定位是**索引加常识，不超过 300 行**。

| 节 | 写法 |
| --- | --- |
| 项目定位 | 一句话：项目名和定义、核心能力列一行、上游仓库 |
| 核心架构 | 一段话，加指向项目地图、应用架构图、技术架构图、模块依赖图的链接，不用文字重画 |
| 关键模块 | 小表格：模块 + 一句话职责，附一行依赖链（注明有没有循环依赖），详情链接到项目地图「模块说明」。多个库、非主库存储各用一张小表 |
| 关键约定 | 只写这个项目特有的硬规则（统一响应包装、异常处理、命名风格、分层），从代码反推，每条附一个代码位置；不写通用套话 |
| 怎么跑 | 一句话，加指向 `make-skill-legacy-takeover-output/2-dev-setup.md` 第 2 节的链接（阶段 B 补全） |
| 禁区 | 只写占位：`<!-- 待人工填写：哪些代码不能动、哪些字段有对接方依赖、哪些配置改了会出事。线索见 make-skill-legacy-takeover-output/README.md 第六节「疑点」 -->` |
