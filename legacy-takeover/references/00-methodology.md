# 00 方法论总纲

所有阶段的执行规格都建立在这份认知上。

## 1. 为什么同一个工具，有人改得稳、有人改完就出事

差别在用法，不在 AI。动手之前，先告诉 AI：项目是做什么的、哪里有雷、哪些接口不能碰。这一步要当成投资来做。

典型事故：给一张表加了个字段，线上另一个接口炸了。原因是这个字段六年前被一个早已下线的对接方隐性使用，只有已经离职的同事知道。

老项目难的地方在代码之外：写着「不要删」的注释、离职的前辈、隐性的约定、当年的历史决策。

## 2. 九步链路（AI 来之前，人是怎么接手老项目的）

| 步 | 动作 | 要点 | 完成标志 |
| --- | --- | --- | --- |
| 1 | 找人聊 | 把疑点列成清单，去问产品、架构师、运维。问不到的标「未知」，先搁置 | 疑点清单 |
| 2 | 翻资料 | README、docs、wiki、群聊记录、需求单，只求一个整体感觉 | 粗轮廓 |
| 3 | 浏览代码结构 | 有哪些模块、哪些是核心、哪些是工具类、哪些很久没动过，在脑子里画一张粗地图 | 模块地图 |
| 4 | 搭环境跑起来 | 依赖版本、配置、VPN。跑起来才能打断点、看真实的数据流 | 能启动 |
| 5 | curl 访问核心接口 | 验证真的跑通了，看清输入输出，能复现问题 | 接口通了才算「初步了解」 |
| 6 | 带疑点深挖代码 | 回头处理「未知」：谁在调用、什么时候加的、有没有类似的链路 | 疑点闭合 |
| 7 | 画核心链路 | 主流程从入口到出口，核心表的关系，外部依赖 | 链路图 |
| 8 | 动手改 | 小步改：改一处，跑通，确认没有副作用，再改下一处 | 改动完成 |
| 9 | 验收 | curl 核对主流程、跑相关的业务场景、找人 review | 三项齐全才算完成 |

时间比例很反直觉：70% 花在理解上（第 1–6 步），30% 花在改造上（第 7–9 步）。

冷启动可能要一两天到一两周，会焦虑，但这是投资。第一个任务磨两三天，第二个一天，第三个几个小时。

最常见的反模式：跳过前六步，直接把一段代码贴给 AI，问「这个项目是做什么的」，然后让它改。上下文是空的，出了问题反过来怪工具。

## 3. 三档分工（Claude Code 进来后，哪一步变了）

| 档 | AI / 人 | 哪些步骤 | 用法 |
| --- | --- | --- | --- |
| 第一档 AI 主导 | 80 / 20 | 翻资料、浏览代码结构、访问接口 | AI 出初稿，人花几分钟校一眼。要快，不放手就没有价值 |
| 第二档 人机对半 | 50 / 50 | 找人聊、搭环境、带疑点深挖、画核心链路、动手改 | AI 整理疑点清单、写启动脚本、画架构图和链路图、写代码和测试；人负责找谁问、内网和库的权限、补业务约定、选方案 A 还是 B、决定是否重构、定边界条件 |
| 第三档 人主导 | 20 / 80 | 判断哪些代码能动、对接方是谁及其诉求有没有变、最终验收、上线风险（回滚成本、灰度、影响面） | 要稳。不要问 AI「你觉得呢」，它的答案不承担责任 |

两个反模式：过度依赖（把 AI 当成什么都能干的外包），过度保守（还在手动读 README、手动画图）。

最危险的情况：AI 做完 80%，人把剩下的 20% 当成 0。AI 的摘要很完整、代码很干净、测试全过，上线却炸在一段写着「不要删，某对接方需要」的逻辑上。**20% 的盲区，常常就是 100% 的事故。**

AI 改变的是节奏（了解阶段从一两周压到半天），不是链路。

## 4. 三层控制（让 AI 可信）

| 层 | 目标 | 怎么做 | 资产 |
| --- | --- | --- | --- |
| 理解层 | 让 AI 看见 | 整理项目用途和核心场景、架构和关键模块、对外和内部接口、表关系和字段含义、隐性约定 | 三张全景图、接口清单、数据模型、CLAUDE.md |
| 约束层 | 让 AI 听话 | **静态约束**写进 CLAUDE.md 和 SKILL.md，长期复用（「某兼容类改动必须保持方法签名」「只动要改的文件，不顺手重构」）；**动态约束**每次写在提示词里（「只改这三个文件」「先确认方案再动代码」「不确定就停下来问，不要猜」） | CLAUDE.md、SKILL.md、提示词 |
| 验证层 | 让 AI 可信 | 动手前先建安全网：集成测试锁住核心链路，Characterization Test 锁住说不清楚的老逻辑，独立 review（换个视角，比如攻击者视角），curl 对比改造前后的响应 | 测试、CI、curl 记录 |

三层是互相喂养的：理解决定约束，约束决定验证，验证暴露出来的边角场景又反哺理解（补进 CLAUDE.md）。

它们不是先后流程，而是时刻在工作的骨架：回答 AI 一个字段是什么意思，就是在沉淀理解；加一句「不要改测试文件」，就是在加约束；补两个 case，就是在做验证。

和九步的对应：前六步主要在建理解层，第 4–5 步开始带上约束，第 7–8 步三层同时起作用，第 9 步以验证为主。

验证的基准必须独立于 AI 的产出。AI 擅长生成，不擅长判断自己写的代码对不对；它自己写的测试，覆盖不到它自己没意识到的情况。

## 5. 三种债和三种风险

**三种债**

| 债 | 是什么 | 用什么还 |
| --- | --- | --- |
| 理解债 | 代码产出的速度远远超过你真正理解代码的速度 | 读懂陌生代码，写进 CLAUDE.md 留住认知 |
| 验证债 | 代码看起来对，不等于真的对。多数开发者不完全信任 AI 的产出，但并不是每次都 review | 改造前护栏 + Characterization Test |
| 改造路径债 | 第一次翻译出来的方案不一定是最优路径，不停下来反问，后面全建在错的地基上 | 「路径选对了吗」的反问 |

老项目还有一笔「棕地税」：上下文占用超过约 40% 以后，质量开始下降（解法是压缩上下文、蒸馏成文档）、跨会话会遗忘（解法是 CLAUDE.md）、不知道历史就会给出不兼容的方案（解法是用 MCP 接入历史数据、人来补充）、有经验的人反而被拖慢（解法是用 SKILL.md 固化流程）、上下文溢出（解法是 Context Map，即 docs 索引）。

**三种风险**

| 风险 | 解药 |
| --- | --- |
| 方向错：AI 顺着你的提问给方案，可你的问题不一定问对了 | 显式拍板关键决策点 |
| AI 偷懒：在边界 case、warning、你不熟的技术栈上，用 `allow` 或泛化的兜底糊弄过去 | 工程师 review，不留 allow |
| 工程师跟不上：越用越快，对代码的真实把握越来越浅，AI 出了 bug 你已经不会修了 | 让 AI 当助教，而不是写完就走的合伙人 |

## 6. 经典方法：Characterization Test 和 Seam

出自 Michael Feathers《Working Effectively with Legacy Code》（2004），在 AI 时代重新成为刚需。

**Characterization Test**：不测代码「应该做什么」，只锁住它「现在实际做什么」。

1. 把要锁的代码放进测试框架。
2. 写一个必然失败的断言。
3. 用失败信息读出它真实的行为。
4. 把断言改成和真实行为一致。

这样就得到一条行为基线，用来对抗「沉默的行为偏移」。

**Seam（接缝）**：不改这里的代码，也能改变它行为的地方，比如可以覆写的方法、配置注入、把静态调用改成接口。没有接缝的代码被 AI 改，风险和爆炸半径都更大。

推荐顺序：先用 Characterization Test 锁住行为，再用 Seam 隔离，最后重构。

## 7. 武器库：够用就停

| 类别 | 代表 | 在本 SOP 里怎么用 |
| --- | --- | --- |
| AI 编码 Agent（主武器） | Claude Code、Codex、Cursor、Copilot、Cline、Aider | 选一个用熟。Claude Code 和 Codex 效果相当 |
| 上下文管理（老项目最核心） | CLAUDE.md、AGENTS.md、SKILL.md、记忆系统 | 把上下文从「每次口述」变成「常驻、自动读」 |
| 能力扩展 | MCP（GitHub、数据库、内部系统）、Sourcegraph | 按需接。一个 MCP 都不接，也能完整做完改造 |
| 规范驱动 | Spec-Kit、OpenSpec、Kiro | 本 SOP 不用。老项目没有清晰的 spec，「先约束再动手」的思想已经包含在三层控制里 |
| 工程辅助 | SonarQube、测试框架、CI 门禁、跨模型互审 | 验证层大量落在这里 |

| 场景 | 组合 |
| --- | --- |
| 接手陌生项目的第一天 | Agent + 上下文管理（项目大的话加 Sourcegraph MCP），沉淀进 CLAUDE.md |
| 小 bug | 只用 Agent，给出相关文件和需求，自己 review |
| 跨模块的中等改造 | Agent + CLAUDE.md + SKILL.md + 测试 + CI |
| 陌生语言加陌生项目 | Agent + CLAUDE.md + MCP + 语言助教模式 |
| 高风险改造 | Agent + 专项 SKILL.md + 找全调用路径 + 多角度独立 review |

遇到新工具，先问三个问题：它属于哪一类？它解决的是理解、约束、验证中的哪一层？相比现有工具，增量是什么？

手里常备两三套能互相替代的工具组合，任何一个被断了都能平滑切换。

## 8. 业界在做同一件事

学术界（读陌生代码库都遵循「全局 → 局部 → 关系」的螺旋）、工具厂商（Anthropic 的 Code Modernization Starter Kit：代码库分析 → 渐进式迁移 → 等价性验证）、咨询公司（用知识图谱做逆向工程；别一次性改造整个系统；代码之外的语境只在领域专家的脑子里）、开源工具（Aider 基于 git、可以随时回退；Cline 透明地展示计划和动作），最后都收敛到同一个三段式：**理解（让 AI 看见）→ 改造（让 AI 听话）→ 验证（让 AI 可信）**。

## 9. 核心五问（复盘）

1. **这套思路能解决日常的改造问题吗？** 这套方法没有发明新的软件工程，价值在于把「谁做什么、什么时候人停下来介入、什么时候 AI 自主、怎么验证」标准化。它解决的不是「做不做得出来」，而是「每次都稳定在 80 分以上」。
2. **能直接照抄吗？** 能，前提是你认同「慢就是快」。凭经验直接做也有隐性成本：写到一半发现漏了边界要回头改、业务方说不是我要的、老接口被破坏紧急回滚、SDK 客户报错凌晨起来修。这套流程把返工成本集中、显式地花在前面。
3. **流程这么多，必须一步步跟吗？** 不是 100%。
   - **可以不走全套**：明确的 bug 修复、改文案或样式、重构独立的工具函数、加内部脚本。
   - **强烈建议跟流程**：多模块、多 service 协同；前后端联动；老接口有外部依赖（SDK 客户、其他系统）；多人协作同一个特性；有历史包袱（CLAUDE.md 里有禁区）。
   - 跑熟 5–10 次以后，流程会内化成一张清单：拿到需求先想业务目标、边界场景、不在范围的事；动手前想影响范围和关键决策点；改完必须跑测试、看 `git diff`、检查老代码有没有被顺手改。
4. **为什么没用什么高级工具？** 核心是工作流，不是工具。工作流有五段：理解项目、拆需求、拆方案、改代码（小步 + 测试 + review）、沉淀（更新资产，把教训写进 CLAUDE.md）。用到的工具很朴素：CLAUDE.md、SKILL、docs-auto-sync、Characterization Test、CI、环境脚本。
5. **按思路跑了，效果还是不好？** 99% 是该停的地方没停。三种显性失败，各配一个自查问题：
   - 拆需求时偷懒：业务目标照搬 AI 的、待决策的边界让 AI 默认填、范围只有候选没拍板。自查：业务目标是谁写的？每条边界有没有人拍板的产品决策？范围有没有最终决定？
   - 跳过方案第 7 节的决策点审核：扫一眼觉得挺全就进了下一步，结果破坏性变更（比如组件 props 变了）到改前端时才暴露。自查：第 7 节每一条，是真看过并给了判断，还是直接点了 OK？
   - 跳过现状确认：整个流程归零。自查：开工前，有没有亲自点过产品？

   还有一种隐性失败：不够细心。对 AI 的某个判断有疑虑却没追问，或者某个 review 点没有逐字看，被 AI 塞进了不一致的实现。每一次判断层面的「算了，不追问了」，都是流程上的一个漏洞。

   **本技能的对应做法**：AI 按推荐方案往前推，但这三类判断都会以「AI 推荐，待确认」标注出来，集中写进总说明「待你确认的 AI 推荐」的最前面。用户必须逐条看完，这套流程才算闭环。

**AI 加速的体力活（约 70%）**：写需求文档、扫代码找影响面、写方案并画图拆任务、写大部分样板代码、写测试覆盖大部分边界、同步文档。

**人必须自己扛的判断（约 30%）**：业务目标方向、边界场景的产品决策、不在范围的事、改造前的现状确认、方案第 7 节决策点的审核、测试断言凭实际不凭应该、最终的代码 review。

**分工的变化**

| 阶段 | 以前 | 现在 |
| --- | --- | --- |
| 理解项目 | 人 | 人 + AI 一起理解 |
| 理解需求 | 人 | 人 + AI 一起理解 |
| 开发代码 | 人 | AI 开发 + 人审核 |
| 修复 bug | 人 | AI 修 + 人兜底 |

AI 当调研员，人当决策员，还要当兜底员。兜底员的典型动作，是自己打开产品点几下。这件事 AI 做不了。

## 10. 四个动作

1. **读懂陌生代码**：给 AI 一份拆解框架，让它把项目展开，再把认知写进 CLAUDE.md 留住。这是后面所有动作的地基。
2. **建好改造前护栏**：先能跑起来，再有兜底测试，才有底气提交。Characterization Test 把「此刻系统的行为」凝固成可执行的代码。
3. **用提示词驱动产出**：普通场景下，驱动 AI 写代码、跑测试、提 PR；在不熟的技术栈上，让 AI 当助教，边写边解释关键机制，人做判断。
4. **显式拍板关键决策点**：AI 给出 80 分的初稿，人要做的不是把它改到 95 分，而是先判断它是不是建立在正确的方向上。

前三个动作 AI 大量参与，第四个只能由工程师自己做。工程师真正的角色，不是用 AI 的人，而是对 AI 的产出负责的人。

## 11. 飞轮

老项目改造像推一辆满载的大卡车：冷启动很慢。熬过去以后，CLAUDE.md、SKILL.md、验收体系一点点积累起来，理解越深，文档越厚，上下文越准。到第三个任务，基本就不用手把手带 AI 了。
