# 阶段 E　挑战开源

场景：代码不是你的，bug 也不是你的，你把改动贡献回去。目标是产出两个 PR（第一个用来走通流程，第二个要有技术含量）和一个高质量的 issue。

开源 commit 公开可验证、不可伪造、AI 写不出来，所以在 AI 时代反而更值钱。

**只能由人做的事**：
- fork（GitHub 账号操作）；
- 选哪个项目、选哪个 issue、选哪个修复方向；
- 审批 plan；
- 提交前 review 代码；
- push、提 PR、提 issue，以及之后和维护者沟通。

**耗时参考**（用于「超过预估 1.5 倍就停」的规则）：第一个 PR 30–60 分钟；第二个 PR 1–1.5 小时；issue 30–45 分钟。

本阶段里，这些点各**问用户一次**，或者准备好材料交给用户。**本技能不执行 push、`gh pr create`、`gh issue create`**：命令和 PR / issue 正文都准备好，写进 `contributions.md`，由用户自己执行。

本阶段的产出都在 `make-skill-legacy-takeover-output/`：总说明 `README.md`、`1-oss-map.md`（E4 的项目地图）、`2-contributions.md`（模板 `templates/contributions.md`，下文简称 contributions.md）。

**两种运行方式**（见 SKILL.md 第 2 节）：只读（默认）做 E1、E2、E4、E5、E7：选项目、找入口、摸项目、筛 issue、扫问题写 issue 正文，第一个 PR 的改法写成具体的改动说明放进 contributions.md。E3、E6 要建分支、改文件、跑检查和测试、commit，只在用户说「跑起来」后做，而且只在用户自己 fork 的仓库里做。

## E1　选项目（还没选定项目时）

开第一个口子有三个常见误区：
- 项目太顶级：review 周期长，信心会被磨没；
- PR 太简单：一个改错字的 PR 写在简历上没有说服力。所以第一个 PR 只用来走通流程，不能是唯一的贡献；
- 心里没标准：在 Trending 上刷几个月也选不出来。

下面的三道题，就是用来建立这个标准的。

执行规格：

```plain
我想开始给开源项目贡献代码,作为我的第一个开源 PR 的目标项目。

我的筛选标准是三道题:
1. 有真实技术含量,不是 demo 项目
2. 正在快速成长但还没到顶级(几百到几千 star、有持续 commit、
   有几个核心维护者,但还没到几万 star、没成为行业标准)
3. 跟我的技术栈或职业方向有关联

我的背景:<用户的方向和技术栈；不知道就先问一次>

按这三道题给我推荐 5 个候选项目。每个项目说清楚:
- 项目定位
- star 数和最近一年的 commit 活跃度
- 维护者背景(独立团队还是大公司主导)
- 为什么适合我作为第一个 PR 目标
- 它的 good first issue 入口在哪
```

自检：
- [ ] 每个候选都满足三道题。star 超过 5 万，或者最近 3 个月没有 commit 的，砍掉
- [ ] 补查 AI 推荐之外的隐性信号（能用 `gh` 查就查）：PR 从提交到第一次 review 是否超过一周（超过的对新人不友好）；核心维护者是不是只有 1–2 个人；最近 6 个月有没有新的贡献者合入（有，说明新人路径走得通）

把候选交给用户挑选。用户 fork 并 clone 以后，在仓库目录里继续。

## E2　找第一个 PR 的入口

执行规格：

```plain
我刚把这个项目的仓库 clone 下来了。我要做我的第一个开源 PR,
目标是走通完整流程,不追求技术难度。

请你扫一遍仓库的 README、CONTRIBUTING.md、docs/,看有没有专门
为新人设计的"first PR"入口。比如:
- 项目方贴心准备的简单贡献入口(签名墙、贡献者列表之类)
- good first issue 标签下的 typo 修订或文档补充
- 任何只需要改一行就能体验完整 PR 流程的入口

如果有,告诉我具体路径 + 怎么改 + 怎么提 PR。
```

理想的入口，是项目方为新人设计的签名或名单类入口；没有就找 typo 或文档补充。不要选超过 50 行的 good first issue。

## E3　第一个 PR：走通流程（只在运行方式下）

只读方式：把要改的文件、位置、改法，以及 commit message 和 PR 描述写进 contributions.md，不动仓库。

执行规格（本地部分由你执行，到 push 之前停）：

```plain
我刚 fork 并 clone 了 <项目> 仓库,要 <改什么>,作为我的第一个开源 PR。

请你帮我把整套流程跑完。每一步执行前告诉我你要做什么,执行后告诉我结果。
任何报错立刻停下来问我,不要自己瞎修。

具体步骤:

1. 建一个新 branch,命名规范跟项目已有 branch 风格对齐

2. 找到 <文件>,先看一眼现有格式,
   然后在合适的位置严格按同样格式修改

3. 跑项目自带的代码格式检查或 lint。看 CONTRIBUTING.md /
   pre-commit hook / Makefile,有什么用什么。别瞎跑全量编译,
   这是个 markdown 改动,只跑相关检查就行。有报错就修,跑通为止。

4. 写一条 commit message,Conventional Commits 规范,subject
   不超过 50 字符。然后 git add 相关文件并 commit。

5. push 到我的 fork(remote 名是 origin)。

6. 给我写一个 PR 描述,3-5 行,说明这是我的第一个 PR、
   语气是普通工程师不是 LinkedIn 帖子。

7. 如果系统装了 gh CLI,直接 gh pr create 把 PR 提了。
   没装就把 PR 描述输出给我,我自己去 GitHub 点提交。
```

签名类入口要用到个人信息（名字、邮箱、日期）。名字和邮箱只从 `git config user.name` / `git config user.email` 读取，读不到就问用户一次；日期用当天的。不编造，也不从别处找。

本技能执行第 1–4 步和第 6 步。第 5 步和第 7 步的命令，连同 PR 描述一起写进 `contributions.md`，由用户执行。

三个护栏：
- 每一步执行前先说明、执行后汇报，报错立刻停；
- 不要为了一个文档改动跑全量编译；
- 有 gh CLI 就用，没有就退回人工提交。

## E4　第二个 PR：带任务摸项目

执行规格：

```plain
我在 <项目> 仓库目录下。现在要做第二个 PR,目标是给 <项目> 提交一个
有真实工程价值的小贡献。

请你按这四个维度给我一份针对"找 issue"任务的项目地图:

1. 模块划分。代码大致分成几块?每块负责什么?
2. 测试组织。单测放在哪、集成测试放在哪、怎么跑?
3. 贡献热点。最近三个月哪几个模块改动最多?活跃 contributor 主要在
   哪些模块?(扫 git log 看)
4. 适合新人的入口。看 issues 里 good first issue / help wanted
   标签下,有没有可以上手的方向?CONTRIBUTING.md 有什么对新人的硬约束?

不要给我一份完整架构文档,只给我对找 issue 有帮助的那部分。
```

产出 `make-skill-legacy-takeover-output/1-oss-map.md`（开工时已经把产出目录加进 `.git/info/exclude`，确认它不会被提交进 PR）。

## E5　筛 issue（问用户一次）

执行规格：

```plain
基于 make-skill-legacy-takeover-output/1-oss-map.md 那份项目地图,帮我从 issue 列表里筛 5 个
候选,作为我的第二个 PR 目标。

筛选标准:
1. 改动量不大,代码 + 测试加起来 50-200 行
2. 描述清楚,改动是局部的(单文件或单模块内)
3. 不需要深度业务理解,我能 review 得了 AI 写的代码

每个候选告诉我:
- issue 编号和标题
- 它在哪个模块
- 我做这个 PR 大概要干什么(一两句话)
- 为什么它符合上面三条标准
- 风险点在哪(比如有没有可能改完发现规模超出预期)

5 个候选给我排个优先级,从最稳到最有挑战。
```

自检：
- [ ] 每个候选都列了风险点，尤其是「看起来 50 行、实际可能 500 行」的情况，并写明「改到哪一步就该停下来」

把候选交给用户挑选。issue 的选择和修复方向，AI 替人拍板是最危险的。

## E6　实现第二个 PR（只在运行方式下）

只读方式：用户选好 issue 以后，把实现思路、要改的文件、风险点和改到哪一步该停写进 contributions.md，不动仓库。

执行规格：

```plain
我要给 <项目> 提一个 PR,实现 issue #XXX:[一句话需求描述]。

请你帮我把整套流程跑完。每一步执行前告诉我你要做什么,执行后告诉我结果。
任何报错或不确定的地方立刻停下来问我,不要自己瞎修。

具体步骤:

1. 先读 issue #XXX 的完整描述,然后读相关代码:这个 issue
   涉及的模块当前实现长什么样、它依赖哪些 API、上下游有哪些关键调用。
   读完给我一份"我要改什么"的简短 plan(3-5 条)。我审核 plan
   之后才能进下一步。

2. plan 我同意之后,建一个新 branch,命名跟项目风格对齐。

3. 按 plan 写代码。我对这门语言不熟,所以你写完之后:
   - 关键改动逐段告诉我"这里在做什么、为什么这么写"
   - 任何用到语言特有机制的地方(所有权 / 生命周期 / async / 并发安全等),简短解释
   - 不要为了炫技用复杂的 idiom,选最直白的写法
   - 如果有多种合理写法,选项目现有代码里最常用的那种风格

4. 看测试影响。这次改动相关的现有测试在哪?改完后会不会失败?
   失败的话怎么更新?需要新增测试覆盖什么场景?

5. 跑测试。看项目的 Makefile / CI 配置确认怎么跑测试,
   不要用默认命令假设。跑通为止。

6. 跑 lint(如 cargo clippy)。所有 warning 都要清掉,不要留 allow 注解绕过。

7. 写一条 commit message,Conventional Commits 规范。
   然后 git add + commit。

8. push 到我的 fork。

9. 写一个 PR 描述,包括:
   - 这个 PR 解决的 issue
   - 改动的高层描述(2-3 句)
   - 实现要点(3-5 条 bullet)
   - 测试覆盖了哪些场景
   - 有任何 trade-off 或后续可改进的点,显式说出来

10. 如果装了 gh CLI,直接 gh pr create 提交。没装就把 PR 描述
    输出给我,我自己去 GitHub 提。
```

本技能的执行方式：
- 第 1 步的 plan 交给用户审批（问一次）。
- 第 2–6 步由你执行。第 6 步做完、第 7 步 commit 之前，是必须停下来 review 代码的点：署名的是用户，要对开源项目负责。你先在本地 commit（不推送），在 contributions.md 里写明「commit 前的 review 点：请 review 后再 push，要修改就 amend」，把逐段解释附在旁边。
- 第 9 步的 PR 描述也由你写。
- 第 8 步和第 10 步的命令写进 `contributions.md`，由用户执行。

自检：
- [ ] 测试命令是从 Makefile / CI 里找出来的（有的项目用的是 nextest 这类工具，不是默认命令）
- [ ] warning 清零，没有 allow
- [ ] 逐段解释写进了 contributions.md，供用户 review 时对照
- [ ] 测试失败时先停下来，把错误给用户看，再修

## E7　高质量 issue

扫描执行规格：

```plain
帮我扫一遍代码,找潜在的性能问题。重点看:
<按语言列出的典型问题，如：热路径上不必要的拷贝、async 里持有同步锁、
锁粒度太粗、循环里反复分配、迭代器用法低效>

不要找 lint 已经能查出来的(CI 自己会跑)。
找那种需要看上下文才能发现的真问题。

给我 5 个候选,每个说清楚:
- 文件路径和行号
- 问题描述(具体哪段代码 + 为什么是问题)
- 影响范围(只有 corner case 才会触发,还是日常路径上)
- 修复思路(不要写代码,讲清楚改动方向就行)
```

选择标准（交给用户挑选时附上你的推荐）：
- 选算法层面有改进、修复方向需要讨论的问题；
- 一行就能改掉的风格问题，直接提 PR 就行，不值得开 issue。

issue 正文的执行规格：

```plain
基于上面那个 [具体问题描述] 的性能问题,帮我写一个 GitHub issue。

要求:
1. 标题简洁,一句话概括问题(<80 字符)
2. 正文按这几节:
   - Description:问题是什么,3-5 句话,讲清楚核心复杂度或机制问题
   - Reproduction:怎么复现(具体条件 + 触发路径)
   - Impact:影响什么场景、严重程度,生产环境量化一下
   - Suggested fix:列出 2-3 种可行的修复方向(不要写代码,讲思路),说明我的倾向,请维护者对齐
   - Environment:项目版本、语言版本、OS
3. 语气是普通工程师,不是 LinkedIn 帖子,不是问问题,是报告问题
4. 显式说"我可以在确认方向后跟一个 PR"
```

正文写进 `contributions.md`，由用户提交。

## E8　收尾：contributions.md 和总说明

先写 contributions.md，再按 SKILL.md 第 9 节补全总说明 `make-skill-legacy-takeover-output/README.md`（做了什么、需要你执行的 push / gh 命令、每个产出的作用）。

按 `templates/contributions.md` 写，内容包括：
- 每个产出（分支、提交号、PR 描述、issue 正文）；
- 要用户执行的 push / gh 命令；
- 用户应该重点 review 的地方。

**节奏提醒**（写进 contributions.md 末尾）：
- 第一个 PR 等 review 的空窗期，可以并行去筛第二个 issue；
- PR 被 close 是常态：礼貌地问原因，代码留在自己的 fork 里，换一个 issue 继续；
- 持续比单次重要：每周哪怕提一个文档级的小 commit，也去 review 别人的 PR，在设计讨论里发声；
- AI 时代，维护者的注意力更稀缺。光会用 AI 提 PR 不够，还要展示你对项目方向的理解、取舍判断和沟通的分寸。
