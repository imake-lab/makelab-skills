# legacy-takeover：老项目改造执行规程

这份文件写给执行它的智能体。**用户不需要做任何操作步骤**：用户触发以后，由你按本规程自主推进，把交付物写进 `make-skill-legacy-takeover-output/`，最后交一份总说明 `make-skill-legacy-takeover-output/README.md`。只有遇到第 5 节列出的那几件「只有人知道」的事，才收集起来，写进总说明，或者集中问一次。

开工前先读 `references/00-methodology.md`（方法论总纲），所有判断都以它为准。

## 1. 判断模式

根据用户的话和项目现状，选一种模式。拿不准就按「接手」处理。

| 模式 | 触发 | 执行 | 交付 |
| --- | --- | --- | --- |
| 接手（默认） | 「接手 / 摸清这个项目」，或者只调用了技能、没给需求 | 阶段 A → 阶段 B | 总说明 + 1、2、3 号文档 + apply/ |
| 改造 | 「改造 / 加功能：<一句话需求>」 | 缺 A、B 的资产就先补齐 → 阶段 C | 再加一篇 `4-change-<feature>.md` |
| 二次开发 | 「基于这个开源项目做 <需求>」 | 阶段 D | 见第 7 节 |
| 提 PR | 「给这个项目提 PR / 贡献代码」 | 阶段 E | 见第 7 节 |

| 阶段 | 执行规格 | 说明 |
| --- | --- | --- |
| A 摸项目 | `references/01-understand.md` | 理解项目，沉淀成 AI 能读的资产 |
| B 建护栏 | `references/02-guardrails.md` | 摸清环境和测试，做出补测试计划，接上 CI |
| C 做改造 | `references/03-change.md` | 一句话需求到方案；运行方式下到交付 |
| D 二次开发 | `references/04-secondary-dev.md` | 基于陌生开源框架做需求 |
| E 挑战开源 | `references/05-open-source.md` | 给开源项目提 PR 和 issue |
| 挖 SKILL | `references/06-skill-mining.md` | A、B 阶段都会调用 |
| 技术栈对照 | `references/stack-map.md` | 把规格里的 Java/Spring 示例命令换成项目实际的技术栈 |

## 2. 运行方式：默认只读

老项目在新环境里经常跑不起来，强行安装、启动容易卡住，还可能弄乱用户的机器。所以**默认只读**，用户明确要求时才运行。

| | 只读（默认） | 运行 |
| --- | --- | --- |
| 怎么进入 | 不用说 | 用户说「跑起来」「可以运行」「装依赖跑测试」「跑起来并改造」，或者在只读做完以后这么说 |
| 能做的 | 读文件、grep、看 git 历史（`git log`、`git status`、`git rev-parse`），写 `make-skill-legacy-takeover-output/` | 另外可以安装依赖、编译、启动、调接口、跑测试、写测试和代码 |
| 不做的 | 不安装、不编译、不启动、不跑测试、不起 Docker；不改项目里 `make-skill-legacy-takeover-output/` 以外的任何文件 | 不做第 6 节禁止的事 |
| 阶段 B | 依赖清单、环境脚本、上手步骤都从配置文件推出来，标「未实测」；核心链路、测试现状（静态）、缺口、补测试计划、CI 配置照做。B3 编译启动、B4 冒烟、B8 跑测试、B11 补测试跳过 | 全部执行 |
| 阶段 C | 现状只做静态核对，不提问；出需求和方案，方案过一次独立 review，验证部分写成「待验证清单」。**不改代码** | 开工前问一次现状，然后改代码、补测试、验证；方案和代码各过一次独立 review；回灌 |
| 阶段 D、E | 只出文档（框架地图、方案；项目地图、候选 issue、issue 正文） | 装框架、写扩展代码；在 fork 里实现 PR |

只读方式下跳过的任务，在总说明的进度表里标「跳过（只读）」。用户之后说「跑起来」，就从进度表接着做这些任务，把结果补进同一份文档，不另建文件。

## 3. 执行方式

1. **先做体检**：
   - 识别技术栈（读 `stack-map.md`）；
   - 看有没有 `make-skill-legacy-takeover-output/README.md`：有的话，从它第八节「进度」记录的位置接着做；
   - 判断运行方式（第 2 节），写进总说明的进度。
2. 建立产出目录 `make-skill-legacy-takeover-output/`（见第 7 节），先从 `templates/output-README.md` 建总说明 `README.md`。之后每完成一个任务就更新它的进度表，中断后可以从这里恢复。
3. 按规格文件里的任务编号顺序执行。每个任务都按「执行规格 → 产出 → 自检」走：
   - **执行规格**：经过实战验证的提示词，照着它做。尖括号里的占位符按当前项目填入。提示词里的「保存到…」，一律按规格文件写明的位置，写进对应文档的对应小节。
   - **产出**：写到约定的文档和小节。
   - **自检**：逐条核对，不合格就自己重做。
4. 每个阶段结束时，运行 `python3 <本技能目录>/scripts/check_takeover.py --root .`。有「错误」先修，再进入下一阶段。
5. 全部结束后，按第 9 节收尾：补全总说明，然后在对话里简要汇报。

## 4. 自主原则（全程适用）

- 自主推进，不要每一步都问用户。判断不清的地方，先做一个合理选择，在总说明里标出来。
- 每一步做完，自己 review 输出质量，不合格就自己重做。图里有漏、有错、有不清晰的地方，主动补充或重画。
- **产出要少而精**：只写第 7 节列出的文件，内容写进对应文档的小节里，不另建零散文件。用户要看的东西越少越好。
- 失败了自己 debug、自己修（换源、换版本、装前置依赖、重试）。**同一个错误连续 3 次修不好，就停止这一项**，把卡点写进总说明，继续做不依赖它的其他任务。
- **Characterization Test 失败是硬停止**，不适用「同一个错误修 3 次」的规则：不许改断言迎合，也不许改老方法。处理流程见 `03-change.md` C12。
- 实际耗时超过预估的 1.5 倍，停下来，把这一项记进总说明。预估参考下面的数字，按项目规模调整：阶段 A 20–40 分钟；阶段 B 只读 20–40 分钟，运行 1–2 小时（环境约半小时，补测试占大头）；阶段 C 只读约 1 小时，运行 3–4 小时；阶段 D 4–5 小时；阶段 E 的各项见 `05-open-source.md`。
- 清单都有数量上限，宁少勿多，P0 和 P1 分层。超出上限，你自己先砍到上限以内。但要注意，有些数字是**下限**，不受这条上限约束：边界场景至少 8 条；改造点要把后端、前端、测试、文档都列全。
- 上下文占用超过约 40% 以后，质量会开始下降。长任务要及时把已经确认的结论落盘到 `make-skill-legacy-takeover-output/`，以文档为单一事实源继续往下做，不要依赖长对话里的记忆。
- 补测试每批 1–3 个，最好 1 个。一批跑通了，才开始下一批。
- **测试断言凭「实际跑出来是什么」写，不凭「应该是什么」写。** 所以只读方式下不写测试代码，只写补测试计划。
- 改代码只做当前批次的改造点，不重构现有方法，只调用它们，不顺手改其他文件，对齐项目现有风格。
- warning 全部清零，不加 `allow` / `skip` / `@Disabled` / `xfail` 来绕过检查。跑不了的测试如实标注原因。
- 结构化的东西（JSON、报告）用代码生成，不让 LLM 手写。
- **所有的图都是 SVG 文件**，放在 `make-skill-legacy-takeover-output/diagrams/`。文档里只用图片链接引用，不内嵌 Mermaid 或其他画图代码。画法和自检见 `references/svg-diagrams.md`。画图时打开 SVG 截图检查，不算「运行项目」。
- 读真实文件，不按名字脑补。结论都要标出来源（文件:行号，或配置文件名）。
- **验证的基准独立于被验证的 AI**：改造方案、改造代码各要过一次独立 review（子代理，只给材料、不给你的推理过程），从兼容性、安全、性能三个视角找问题。见 `03-change.md` C9c、C18b。
- **不夸大护栏**：只读方式下，测试护栏只是计划。总说明开头的「护栏状态」必须如实写「只有计划，未实测」，不能让人以为护栏已经建好。

## 5. 只有人知道的事（不编造，统一收口）

下面这些是「AI 做不了、必须由人来」的事。处理方式固定如下：

| 事项 | 你怎么做 | 什么时候问人 |
| --- | --- | --- |
| CLAUDE.md 的「禁区」「历史包袱」 | **只写占位，一个字都不猜**。你找到的线索（写着「不要删」的注释、没人引用却没删的代码、git log 里的反复回滚、可疑的配置）写进总说明第六节「疑点」，并注明「可能属于禁区 / 历史包袱」 | 不中断。写进总说明的「需要你做的事」 |
| 改造前现状确认：功能是不是已经存在 | 先自己静态核对：前端路由、菜单配置、页面文案、已有组件和接口。运行方式下再起服务、用浏览器自动化截图 | 只读方式不提问，结论标「AI 静态核对，待人确认」，写进「需要你做的事」。运行方式在**改代码之前问一次** |
| 需求的三个判断：业务目标、边界场景的产品决策、本期范围 | 按代码和常识给出推荐，在文档里标「AI 推荐，待确认」 | 不中断。写进总说明的「待你确认的 AI 推荐」，排在最前面 |
| 方案第 7 节的决策点 | 按推荐方案写，最终决策栏写「AI 推荐，待确认」 | 不中断。同上 |
| 人亲手验证（curl 看真实 JSON、浏览器操作） | 运行方式下你自己先 curl，有条件就用浏览器自动化截图，记进改造文档的「验证」 | 不中断。总说明里列出要人复核的命令和页面 |
| 需要 sudo、改系统配置、安装系统级软件 | 不执行。写出要执行的命令 | 不中断。写进总说明的卡点 |
| push、提 PR、触发远端 CI、部署 | 不执行。准备好文件和命令 | 不中断。写进「需要你做的事」 |
| 账号密码、Token | 从项目的初始化脚本、样例配置里找默认值；找不到就跳过依赖它的步骤 | 不中断。写进总说明 |

二次开发、提 PR 这两种模式里，有几项选择必须由人拍板，比如路径反问、选哪个 issue。具体见各自的规格文件，那里写明了哪一步要问一次用户。

## 6. 安全措施

- **只读方式下不碰项目**：除了 `make-skill-legacy-takeover-output/`，不新建、不修改、不删除任何文件；不执行任何会改变项目或机器状态的命令。
- **不创建任何分支**，就在当前分支上工作（提 PR 模式在 fork 里建分支除外）。
- 开工时把基线提交号（`git rev-parse HEAD`）记进总说明。
- 运行方式下改代码之前检查 `git status`：工作区不干净，就停下来，告诉用户有哪些未提交的改动，不碰它们。
- 运行方式下，阶段 B 每批测试、阶段 C 每批改造点跑通以后，在当前分支本地提交一次，提交信息以 `takeover:` 开头，写清批次或改造点编号，方便识别和单独回退。**不推送。**
- `make-skill-legacy-takeover-output/` 不和代码一起提交，要不要进版本库由用户决定。
- 不删除任何看起来「没用」的代码、表、字段或配置。
- 不读取、不打印、不提交凭据文件。

## 7. 交付物：一个目录，几个关键文件

**所有产出物都放在项目根目录下的 `make-skill-legacy-takeover-output/` 里**，用户只要看这一个文件夹。文档带编号，从 README 开始按 1、2、3、4 读下去。

```text
<项目根>/
└── make-skill-legacy-takeover-output/
    ├── README.md               总说明：做了什么、需要你做的事、待确认、产出物、疑点、代码改动、进度
    ├── 1-project-map.md        A 项目地图：应用架构、技术架构、模块说明、风险地带、模块依赖、外部依赖、接口清单、数据模型、核心时序、互校
    ├── 2-dev-setup.md          B 环境手册：依赖清单、新人上手、安装记录、启动记录、冒烟结果
    ├── 3-test-guard.md         B 测试护栏：核心链路、测试现状、缺口、补测试计划、CI
    ├── 4-change-<feature>.md   C 改造：需求、方案、验证（每个需求一篇）
    ├── diagrams/               全部 SVG
    │   ├── app-architecture.svg    应用架构图：业务域、模块、使用者、业务流向
    │   ├── architecture.svg        技术架构图：分层、技术组件，底部画外部依赖
    │   ├── module-deps.svg         模块依赖图：循环依赖标红
    │   ├── data-model-er.svg       ER 图
    │   ├── sequence-<名>.svg       核心接口时序图
    │   └── change-<feature>.svg    改造链路与流程图（C）
    ├── scripts/
    │   ├── dev-env.sh              install / start / stop / status
    │   └── docker-compose.dev.yml  需要 Docker 方式时才生成
    ├── screenshots/<feature>/  改造前后的截图（只在运行方式、有浏览器自动化时）
    └── apply/                  要放进项目固定位置才能起作用的文件，结构与目标位置一一对应
        ├── apply.sh                用户确认后自己运行：复制到位，已存在的跳过并列出，不覆盖
        ├── CLAUDE.md               A → 项目根目录（Claude Code 只自动读根目录这一份）
        ├── .claude/skills/
        │   ├── docs-auto-sync/SKILL.md   A → .claude/skills/（放在这里才会被发现）
        │   └── env-bootstrap/SKILL.md    B → 同上
        └── .github/workflows/test.yml    B → CI 平台只认这个目录
```

模板：总说明 `templates/output-README.md`；1–4 号文档 `templates/project-map.md`、`dev-setup.md`、`test-guard.md`、`change.md`；环境脚本 `templates/dev-env.sh`；apply 脚本 `templates/apply.sh`。

- **不加别的文件**。内容多的图宁可把画布加高，也不拆成多张。
- **代码是唯一的例外**（只在运行方式下）：补的测试、改造代码必须写在项目原有的源码和测试目录里，才能编译、运行。它们在当前分支上按批本地提交，不推送；总说明里逐条列出改了哪些文件、对应哪次提交。
- **apply/ 由用户决定**：你不运行 `apply.sh`，也不往项目根目录、`.claude/`、`.github/` 写任何东西。
- **阶段之间怎么用这些文件**：后面的阶段要用到 CLAUDE.md 和两个项目技能时，直接读 `apply/` 下的文件，按里面的步骤执行。
- **项目已有 CLAUDE.md**：`apply.sh` 会跳过它。合并建议（加哪几节、改哪几行）写进总说明第五节。
- **目录冲突**：项目里已经有一个不是本技能建的 `make-skill-legacy-takeover-output/`（里面没有由 legacy-takeover 生成的 README.md），就改用 `make-skill-legacy-takeover-output-2/`，并在总说明里注明。

二次开发模式的交付物：

```text
make-skill-legacy-takeover-output/
├── README.md               总说明（同上，四个决策点写在「待你确认」）
├── 1-framework-map.md      框架地图：四维拆解、白嫖区 / 开发区边界
├── 2-plan.md               方案：第一部分设计（需求 → 设计），第二部分技术方案（设计 → 方案）
└── diagrams/  boundary.svg  run-chain.svg
```

扩展代码属于代码，只在运行方式下写，按方案放在框架要求的位置。

提 PR 模式的交付物：`README.md`、`1-oss-map.md`（项目地图，只写对找 issue 有帮助的部分）、`2-contributions.md`（候选、PR 和 issue 正文、要你执行的命令）。贡献 PR 按开源项目的惯例，在你 fork 里的分支上进行，这是唯一会建分支的情况。这个文件夹不能进入要提交的 PR，开工时就把它加进 `.git/info/exclude`。

## 8. 用户回来更正时

用户看完总说明以后，会指出错误（比如「架构图少了一个 MySQL」）、补写禁区和历史包袱、确认或推翻推荐，或者说「跑起来」。处理原则：

- **任何一处更正，都要同步修改所有引用到它的地方**：图、项目地图、CLAUDE.md、改造文档。改完回跑一次 docs-auto-sync，确认没有差异。
- 用户确认或推翻的推荐，把文档里的「AI 推荐，待确认」改成最终决定。被推翻的，要评估已经写好的方案或代码受不受影响，受影响的列出要返工的改造点。
- 用户写好禁区和历史包袱以后，回头检查已有的方案和代码有没有碰到禁区，碰到了就列出来。
- 用户说「跑起来」：切到运行方式，从进度表里标「跳过（只读）」的任务接着做，结果补进原文档，把「未实测」的标记改掉。

## 9. 收尾：总说明

1. 运行 `check_takeover.py`，修掉所有错误。
