# 阶段 C　做改造

目标：从「leader 给一句话需求」走到「需求 + 方案 + 后端代码 + 测试 + 前端跑通 + 文档全部同步」，完成一次完整的改造闭环。

**产出只有一篇文档和一张图**：`make-skill-legacy-takeover-output/4-change-<feature>.md`（模板 `templates/change.md`，分「需求」「方案」「验证」三部分）和 `make-skill-legacy-takeover-output/diagrams/change-<feature>.svg`（链路与流程图）。运行方式下另有截图 `screenshots/<feature>/`。

**两种运行方式**（见 SKILL.md 第 2 节）：
- **只读（默认）**：C0 只做静态核对、不提问 → C1–C9 出需求和方案 → C9c 方案独立 review → 验证部分写「待验证清单」→ C20 收尾。**不改代码**，C9b、C10–C19 跳过。
- **运行**：C0 起服务核对、问用户一次 → C1–C9 → C9c 方案独立 review → C9b 回灌 → C10–C18 改代码、补测试、验证 → C18b 代码独立 review → C19 回灌 → C20。

**前提**：阶段 A、B 的资产已经就绪（项目地图、环境手册、测试护栏、CLAUDE.md 齐全；运行方式下还要项目能跑、护栏到位）。缺什么，先执行对应阶段补上，否则后面所有「基于 make-skill-legacy-takeover-output/…」的步骤都没有素材。本阶段说的 CLAUDE.md，指项目根目录那份（用户已经运行过 apply.sh）；没有的话，就读 `make-skill-legacy-takeover-output/apply/CLAUDE.md`。

**输入**：用户给的一句话需求（可以带一个接口雏形）。下文用 `<feature>` 表示需求的英文短名（如 `prompt-version-diff`），由你根据需求起名。

**本阶段的核心心法**：AI 在数据和代码层面强，在业务判断层面弱。AI 当调研员，人当决策员，还要当兜底员。

## C0　现状确认（硬约束，不能跳）

这条约束来自一次真实的翻车：需求、方案、后端、前端全部做完，才发现「版本对比」功能早就存在。旧按钮并行调两次单版本接口、在浏览器里算 diff、渲染进现成的弹窗。改造完成后，页面上出现了两个做同一件事的按钮。

原因有三：
- 拆需求时，AI 只扫了接口清单，没看到 diff 接口，就答「没有」；
- 拆方案时，AI 看到了弹窗组件，却默认它是配套某个接口的零件，没有说「这个组件正在工作」；
- 人当了甩手掌柜，开工前没有点一下产品。

**AI 扫代码，无法发现「功能已经存在」。**

你要做的：
1. （运行方式）用 `make-skill-legacy-takeover-output/scripts/dev-env.sh start` 起依赖，再起后端和前端，从初始化数据里找到默认账号。只读方式跳过这一步。
2. 尽量自己核对，留下证据（只读方式只做静态的几项）：
   - 在前端代码里搜需求相关的关键词：页面文案、按钮名、路由、菜单配置；
   - 找相关组件，看它被谁调用、调的是哪些接口；
   - 后端搜相近的方法和接口；
   - （运行方式）有浏览器自动化工具（Playwright 等）时，登录后按需求路径截图，存到 `make-skill-legacy-takeover-output/screenshots/<feature>/before-<页面>.png`；
   - 想想同类「人看一眼就知道」的信号：访问日志、监控里有没有这个功能的调用。
3. **只读方式：不提问**。把结论和证据写进改造文档开头，标「AI 静态核对，待人确认」，并在总说明「需要你做的事」里请用户打开产品点一遍。静态证据已经显示功能存在的，按下面第 4 步「已存在」处理。

   **运行方式：改代码之前问用户一次**（这是本阶段唯一一次提问），把你的证据附上：

   ```plain
   需求：<一句话需求>
   我核对到的现状：<证据摘要：相关页面/组件/接口，截图路径>
   请你打开产品点一下确认：这个功能现在是 已存在 / 部分存在 / 不存在？一两句话描述现状。
   ```

4. 拿到回答（或只读方式下用你的静态结论）后，执行规格：

   ```plain
   我打算做一个新需求："<一句话需求>"。
   我已经在产品上点了一遍，确认这个功能[已存在 / 不存在 / 部分存在]。
   现状描述：[用户的一两句话]。

   基于这个现状，告诉我下面的改造路径应该怎么定：是新增、重构、还是优化？
   给一个判断 + 理由。
   ```

   判断和理由写进改造文档的头部。**已存在**的，需求性质就变了：停下来，把「建议改为重构 / 优化，原因是…」写进总说明，等用户重新定方向，不要继续往下做。

运行方式下用户明确说「不用问，直接做」：按你核对的结论推进，在改造文档头部和总说明「需要你做的事」第一条写明「现状未经人确认」。

## 场景一　把一句话需求拆成需求文档

六维体系里，AI 的能力分布：

| 维度 | AI 能力 | 处理方式 |
| --- | --- | --- |
| 接口契约（对齐项目现有风格）、技术性边界（404、空值、超长、并发）、老项目约束（从禁区和历史包袱反推） | 强，85 分以上 | 直接采用 |
| 业务目标、用户场景 | 中，约 60 分，方向容易偏 | 写推荐，标「AI 推荐，待确认」 |
| 边界场景里的产品决策、本期不做的事 | 弱，30 分以下 | 写推荐，标「AI 推荐，待确认」 |

最大的翻车点：草稿看起来已经覆盖了 70%，很完整，于是直接当定稿用。AI 弱的那几个维度会按默认理解被填满，方向一偏，业务方最后会说「不是我要的」。所以这三项必须显式标出来，交给人确认。

### C1　六维拆解

执行规格：

```plain
我有一个新需求：<一句话需求>。
<接口雏形，如 GET /api/xxx?a=..&b=.. 返回 ...（没有就省略）>

读 make-skill-legacy-takeover-output/ 下所有资产(特别是 1-project-map.md 的接口清单和数据模型) + CLAUDE.md，再扫一下代码里现有<需求相关的模块>
相关的实现(<相关的 Controller、Service、Entity>)，
按以下六维写需求文档草稿：

1. 业务目标(一句话)
2. 用户场景(典型场景 + 痛点)
3. 接口契约(方法、路径、入参、返回、错误码，对齐项目现有风格)
4. 边界场景清单(至少 8 条 edge case，包括从现有代码反推的：实体类、建表 SQL、
   数据库配置能看出的字段为 null、超大文本、大小写/排序规则、并发等；
   每条标"基于代码推断"或"待产品决策")
5. 老项目约束(CLAUDE.md 禁区和历史包袱里相关的，每条标 CLAUDE.md 来源)
6. 不在这次范围里的事(先列候选)

输出 markdown，写进 make-skill-legacy-takeover-output/4-change-<feature>.md 第一部分「需求」。
```

结构按 `templates/change.md` 第一部分。CLAUDE.md 的禁区和历史包袱还是占位的，老项目约束就从总说明「疑点」的线索和代码里反推，来源写「代码推断（待人确认）」。

自检：
- [ ] 六维都填上了；边界场景至少 8 条，每条都有预期行为。8 条是下限，不受「清单宁少勿多」的上限约束
- [ ] 每条老项目约束都有来源
- [ ] 「不在这次范围里」有候选清单

### C2　三个判断 + 定稿

这一步本来是人做三个判断（业务目标方向、边界场景的产品决策、本期范围的砍和留），再让 AI 整理成定稿。本技能的处理：你先给出推荐的判断，然后整理成定稿。

执行规格（由你填入推荐的判断）：

```plain
我对 make-skill-legacy-takeover-output/4-change-<feature>.md 的需求部分做了三个判断：

业务目标修正：<推荐的目标表述，以及它对接口返回的影响>

边界场景的产品决策：
- E0x(<场景>)：<处理方式>
- ...

不在这次范围里的事最终决策：
- 砍掉：<…>
- 留到下期：<…>

按以上判断更新需求部分，整理为正式 PRD 格式，保存到原文件。
```

定稿要求：
- 一句话总结放在最前面；
- 接口契约和边界场景用表格；
- 老项目约束单独一节，标明来源；
- 「待产品决策」全部改成具体决定，后面加标记「（AI 推荐，待确认）」。
- 业务目标要把「AI 默认的理解」和「推荐修正后的理解」并列写出来，至少给一个备选方向，并写明它会怎么改变接口返回。实践中的例子：目标从「工程师 review 自己的修改」改成「团队多人协作下的演进追溯」，接口就因此多返回了版本元信息。只给一个结论，人没法判断方向对不对。

这三个判断按原样写进总说明的「待你确认的 AI 推荐」，排在最前面。

## 场景二　把需求文档拆成改造方案

需求讲「做什么」，方案讲「怎么改」。在老项目里，「心里大概有数」远远不够：以为只改一个 Controller，实际会牵动整条链路，连前端也要动。

### C3　摸链路（含前端）

执行规格：

```plain
基于 make-skill-legacy-takeover-output/4-change-<feature>.md 的需求部分，扫一下代码：
- 找出这次改造涉及的完整链路(HTTP 入口到 DB)
- 每个节点说明：文件、类、方法、状态(现有/新增/修改)、关键逻辑(只看相关的)
- 不要漏前端节点(页面、组件、API、类型声明)

输出表格 + 链路图。表格写进 4-change-<feature>.md 方案第 2 节「涉及链路」，
链路图画进 make-skill-legacy-takeover-output/diagrams/change-<feature>.svg 的上半部分。
```

自检：
- [ ] 前端节点列全了。不强调这一点，AI 默认会把需求缩成「加一个后端接口」
- [ ] 「现有组件需要改造」没有被误标成「新建」，否则会重复造轮子
- [ ] 不在主链路上、但会被牵动的节点也检查了：拦截器、AOP、统一异常处理、鉴权白名单

### C4　列改造点

执行规格：

```plain
基于上一步的链路，把改造拆成具体改造点列表(P01， P02， ...)。
后端 / 前端 / 测试 / 文档都列出来，不要漏前端工作量。每条标类型 + 涉及文件
(路径 + 大概行号) + 一句话改什么。写进 4-change-<feature>.md 方案第 3 节「改造点清单」。
```

自检：
- [ ] 前端改造点列全了；测试和文档的改造点也都在
- [ ] 每个要修改老代码的改造点都标了有没有「接缝」（Seam）：不改这里的代码，也能改变它行为的地方，比如可覆写的方法、配置注入、接口。没有接缝、又必须改动的，先在 C10 用 Characterization Test 锁住行为，再制造接缝，最后才改。顺序是锁行为 → 隔离 → 重构
- [ ] 区分了「现有组件改造」和「新建」。没有新增前端依赖的，写明原因（比如现有组件已经能覆盖），避免重复造轮子

### C5　改造流程图

执行规格：

```plain
基于改造点，画一张改造流程图(时序图，SVG，画法见 references/svg-diagrams.md)。
要展示：用户从前端发起请求的完整调用链 + 数据流。
画进 make-skill-legacy-takeover-output/diagrams/change-<feature>.svg 的下半部分(和 C3 的链路图同一张)。
```

有表结构变更的，在同一张图的底部加一块表结构变更；没有的，在方案第 4 节明确写「不改表」。一张图放不下时，宁可把图加高，也不拆成多张。

### C6　影响范围

执行规格：

```plain
基于改造点和流程图，说明影响范围(每条标"高/中/低"风险)：
1. 现有接口受不受影响
2. 现有调用链路受不受影响
3. 测试影响
4. 文档影响
5. 前端兼容性
6. 性能影响

输出表格。
```

自检：
- [ ] 风险没有全标「低」或「中」，每一项都有依据
- [ ] 补查了项目特有的影响：分布式事务、多租户、灰度开关、缓存一致性
- [ ] 先验证假设，再决定复用：要复用的老方法有没有日志、打点、缓存、事务这类副作用？扫一遍，把结论写进「现有调用链路」这一项，据此决定直接复用还是抽一个内部方法。AI 当调研员的价值，就在于验证你以为的坑到底存不存在
- [ ] 对照项目地图「风险地带」：改造点碰到了哪几条（写编号 R0x），每条都写进影响范围，风险等级不低于风险地带里的判断；碰到「无接缝老代码」的，C4 里要有先锁行为、再制造接缝的改造点

### C7　改造步骤和顺序

执行规格：

```plain
基于改造点和影响范围，给出改造步骤和顺序：
- 按依赖关系排序，后端在前、前端跟上、测试穿插
- 每步说明：做什么、依赖、工作量、关键决策点
- 有多个实现方式且优劣明显的，给 2 个方案 + 推荐；
  没有方案分歧的步骤直接给一个方案，不要硬凑多方案

输出表格。
```

自检：
- [ ] 前端的前置依赖写对了：不需要等后端全部完成，接口契约定下来、加上 mock 就能并行
- [ ] 工作量没有估得过于乐观（尤其是前后端联动的部分）
- [ ] 关键决策点是精简过的。「try-catch 还是 if-null」这种小事不要列成决策

### C8　整合成方案文档（关键决策单独抽出来）

执行规格：

```plain
把前面五步的产出整合成完整方案：
1. 一句话概要
2. 涉及链路
3. 改造点清单
4. 改造流程图
5. 影响范围与风险
6. 改造步骤与顺序
7. 待审核的关键决策点(单独抽出来，方便人 review)

第 7 节是关键：把前面散落的所有"需要人决策"的点集中列出来。

写进 make-skill-legacy-takeover-output/4-change-<feature>.md 第二部分「方案」。
```

结构按 `templates/change.md` 第二部分。

自检：
- [ ] 结构是递进的：链路 → 改造点 → 流程 → 影响 → 步骤 → 决策
- [ ] 前面所有标了「需决策 / 建议 / 多方案」的地方，都已经集中到第 7 节

### C9　决策落定

这一步本来是人先逐条拍板第 7 节，再审链路、改造点和影响范围，把发现的问题汇总反馈给 AI 更新。人在这一步常补的有：团队的隐性约束、老接口的副作用、配置白名单、产品的历史决策、过于乐观的工作量估算。

本技能的处理：
1. 自己再审一轮：重点查鉴权白名单、前端交互细节（比如选中两条以后，其他条目要禁用）、工作量。发现遗漏就补一个新的改造点（P13…）。
2. 第 7 节每条决策的「最终决策」栏，填推荐方案，并标「（AI 推荐，待确认）」。
3. 第 7 节原样搬进总说明的「待你确认的 AI 推荐」。

跳过这一步的代价：问题会在写代码时以返工的形式补回来，代价大十倍。所以第 7 节一定要写全，交给人的东西要能逐条确认。

### C9c　方案独立 review（两种运行方式都做）

验证的基准要独立于被验证的 AI。前面的需求和方案都是你写的，自己 review 自己，会漏掉同一套思路里的盲区。所以要换一个没参与过的 reviewer、换视角再看一遍。

做法：用子代理（Agent 工具）开一个独立的 reviewer，**只给它材料，不给你的推理过程**。没有子代理能力时，在总说明「需要你做的事」里给出这段提示词，请用户在一个新会话里运行，或者交给另一个模型（跨模型互审）。

执行规格：

```plain
你是这个项目的独立 reviewer，没有参与这次改造的设计。只看下面这些材料：
1. make-skill-legacy-takeover-output/4-change-<feature>.md 的需求和方案两部分
2. CLAUDE.md，以及 make-skill-legacy-takeover-output/1-project-map.md 的「风险地带」「接口清单」「数据模型」
3. 方案里列出的那些代码文件
从三个视角找问题，每条写：位置(文件:行号或方案章节)、问题、严重程度(高/中/低)、建议:
- 兼容性：现有接口、字段、返回结构、前端调用方会不会被破坏；有没有碰到风险地带却没处理
- 安全：用攻击者的视角找，鉴权和越权、注入、敏感数据外泄、白名单
- 性能：循环里查库、N+1、全表扫描、没有分页、大对象
只报告，不改任何文件。某个视角没发现问题就写"未发现"，不要硬凑。
```

处理：
- 结果写进改造文档「验证」部分的「独立 review」表，对象写「方案」。
- 严重程度为高的，回到方案修正（补改造点、改决策、调风险等级），处理栏写怎么改的；你判断不需要改的，写明理由，并列进总说明「待你确认的 AI 推荐」。
- 中、低的，能顺手改就改，不改的写理由。


### C9b　方案定稿后的第一轮回灌（只读方式跳过）

只读方式不改代码，项目地图要和代码保持一致，所以不回灌，把要回灌的内容写进验证部分的待验证清单。

运行方式下，方案定下来以后、动代码之前，先把这一轮的认知回灌到 `make-skill-legacy-takeover-output/`。这样中途中断，或者只做完后端时，文档和当前状态也是对得上的：

```plain
方案定稿了，把这一轮的新发现回灌到 make-skill-legacy-takeover-output/：
1. make-skill-legacy-takeover-output/1-project-map.md 接口清单：加新接口，标"开发中"
2. make-skill-legacy-takeover-output/1-project-map.md 数据模型：加新增的 DTO
3. make-skill-legacy-takeover-output/4-change-<feature>.md 需求部分：补审核时新发现的边界(如鉴权白名单)
4. 判断新发现的约束是项目级还是一次性：影响所有未来类似改造的列为 CLAUDE.md 候选，
   只这一次的特殊处理留在改造文档的方案部分

输出每份文件改动 diff。
```

## 场景三　跑通后端改造（只在运行方式下）

只读方式到这里为止：把 C10–C19 要做的事写进改造文档第三部分的「待验证清单」（要锁住行为的老方法、要补的单元测试和对应的边界编号、curl 命令、前端入口和操作步骤），然后直接做 C20。

执行阶段，AI 有两个坏习惯：喜欢「顺手」优化老代码；喜欢凭「应该」写测试断言。本阶段用「小步 + review + Characterization Test」压住它们。

四条原则：
1. 小步执行，按改造点分批（例如 P01–P03、P04–P05、P06），每批跑通、自查、提交以后，再做下一批；
2. 自主修复，但同一个错误连续 3 次修不好就停下；
3. 复用现有结构（统一返回包装、ORM 风格、业务异常类、全局异常处理）；
4. 没有测试的改造点，不算完成。

开工前：C0 已经问过用户；确认工作区干净（不干净就停下告诉用户），基线提交号已记在总说明里，再记录基线测试数（跑一次全量测试），写进改造文档的验证部分。**不创建分支**，就在当前分支上做。

### C10　锁住改造前的行为

执行规格：

```plain
我要改造 <实现类> 复用 <要复用的老方法>，
改之前先用 Characterization Test 锁住该方法现有行为。

要求：
- 不要凭"应该是什么"写断言，凭"实际跑出来是什么"写
- 用 <mock 框架> mock <依赖的 Mapper/Repository>，覆盖正常返回 + <不存在时的异常> 两种场景
- 先读实现，记录它实际做的事，再照实际行为写断言
- 不依赖真实数据库
- <该方法不做的事，如状态过滤>，不要凭假设加对应场景
- 测试加在 <实现类所在的模块> 下(实现类在这个模块)
  路径：<测试文件路径>
- 用 <单测命令> 跑，汇报覆盖了哪些场景、每个断言基于的实际值、跑通状态
```

全新代码不需要这一步。只有复用或改动已有行为时才需要。

自检：
- [ ] 断言值来自实际运行；测试放在实现类所在的模块里；在改造前的代码上通过

### C12　实现 Service

执行规格：

```plain
基于 4-change-<feature>.md 的 P04-P05，给 <Service> 加 <方法名> 方法 +
在 <ServiceImpl> 里实现。

- 复用 <老方法>(影响范围已确认无副作用)
- 不要重构 <老方法> 任何细节，只调用它
- <关键实现约束，对应方案第 7 节的决策编号，如 null 处理方式>
- 异常用 <项目的业务异常类> + <错误码>

跑 <测试命令> 确认 Step 10 的 Characterization Test 全过(行为不偏移)。
失败就 stop，告诉我具体哪个测试。
只做 P04-P05，不要做 P06。
```

自检：
实现要点：先做不需要查库的参数校验（比如两个入参相同），再校验主对象存在，最后查数据。每一步都按契约抛对应的错误码。

自检：
- [ ] `git diff` 里，ServiceImpl 只新增了方法和私有辅助方法，原有方法一行没动。格式化造成的改动也要撤销
- [ ] 关键约束逐条对上了。特别是 null 处理要按决策来写：比如「先把 null 转成空字符串，再比较」，和 AI 凭直觉写的「两边都是 null 才算相等」，语义完全不同
- [ ] Characterization Test 全部通过

**Characterization Test 失败怎么处理**（这是硬停止，不适用「同一错误修 3 次」的规则）：
1. 不许为了让测试变绿去改 CT 的断言，也不许改老方法。
2. 先回看测试本身：断言值是不是当初真跑出来的？如果测试写错了，修测试，并在总说明里说明。
3. 测试没错，说明行为真的变了，这正是 CT 要拦住的信号。回退本批改动（`git restore`），把「哪个测试、期望值和实际值、怀疑的原因」写进总说明的卡点，暂停所有依赖本批的改造点。其余不相关的工作可以继续。

### C15　curl 验证 JSON 结构

这一步本来由人做，因为 AI 说「接口跑通了」不可信：JSON 字段名、序列化的问题，单元测试发现不了。

本技能的处理：你先启动应用，自己 curl 一遍，把命令和完整响应记进 `4-change-<feature>.md` 第三部分「验证」；同时把这组命令原样放进总说明「需要你做的事」，请用户亲手再跑一次。

```bash
TOKEN=$(curl -s -X POST http://localhost:<端口>/<登录路径> \
  -H "Content-Type: application/json" \
  -d '{"username":"<默认账号>","password":"<默认密码>"}' | jq -r '.data.<token 字段>')

curl -s -H "Authorization: Bearer $TOKEN" \
  "http://localhost:<端口>/<新接口路径>?<参数>" | jq .
```

自检：
- [ ] `data` 不是 null，嵌套字段都在，字段名和类型都和接口契约一致

2. make-skill-legacy-takeover-output/4-change-<feature>.md 的方案部分

本技能的处理：

## 第二次改造：用脚手架

第一次是搭脚手架，第二次是用脚手架。积累在前，轻松在后。当 `make-skill-legacy-takeover-output/` 的资产、CLAUDE.md 都在，并且已经有一篇完整的 `4-change-*.md` 改造记录时，拆需求和拆方案可以压成一条：

执行规格：

```plain
<口语化的一句话需求，以及对页面或功能的构想>。
按之前的流程，出一篇 make-skill-legacy-takeover-output/4-change-<feature>.md，包含需求、改造影响分析、技术方案。
```

然后：
- C0 现状确认照做，不能省；
- 自己审需求、影响分析、方案三部分。每部分要看什么、为什么必须由人来看（把这个原因写进总说明，提醒人重点看）：
  - 需求：「不在范围」的清单是否合理，用户场景是否真实。AI 容易把「用户没明确要」和「应该不做」混为一谈；
  - 影响分析：跨库、跨模块的风险等级，性能预估是不是太乐观。风险评估依赖对历史包袱的了解，AI 容易拍脑袋给出乐观的结论；
  - 方案：关键决策是否符合团队偏好，目录结构是否对齐项目风格。AI 给的是「业界最佳实践」，不一定是你们团队的最佳实践；
- 把所有「待审核」改成「AI 推荐，待确认」的最终决策；
- C9c 方案独立 review 照做；运行方式下 C18b 代码独立 review 也照做，不能因为是第二次就省；
- 后端也只用一句执行规格（运行方式）：「按 4-change-<feature>.md 的方案，遵循小步原则分批（DTO、Service、Controller、Mapper 各一批），每批跑通 <测试命令>，不重构现有 Mapper，跨库注入参考已有先例，汇报测试总数和失败数」；
- 前端同样一句：「按改造文档的方案实现，不引入新的图表库，全部用现有组件库，改完跑构建」；
- 最后照常回灌。

前提是资产已经攒够。没攒够，就退回上面的分步流程。
